# 技术栈变更决策报告 V2.1

> 文档编号：DEC-TS-01 · 版本 V2.1 · 2026-10-24 · 编写：小凯 · 状态：待管理层/Jason 确认
> 变更内容：后端主力语言 **PHP（Hyperf）→ Python（FastAPI）**；前端明确 **Vue 3 + TypeScript + Element Plus**
> 触发：Jason 决策——「PHP 换 Python + Vue，技术栈更主流」
> 关联：本报告是《自研OMS分析与决策建议书V2》（路径 B 自研）的技术栈层修订；不改变路径 B 决策本身（仍自研、不 fork 商派）

---

## 0. 结论先行

**建议采纳变更**：后端 PHP（Hyperf）→ Python（FastAPI 异步栈），前端 Vue 3 + TS + Element Plus。

一句话理由：**路径 B 已定"不 fork 商派代码、只借鉴业务模型"，当初选 PHP 的唯一硬前提（可复用商派 113 万行代码）已不存在；而新增的 AI 销量预测、K-AIDE Agent 接口两项需求是 Python 生态的主场，团队主技能也是 Python+Vue——换栈是顺水推舟，不是推倒重来。**

需求文档库 **95% 内容语言无关**（业务契约、状态机、事件字典、373 表 DDL 全部不动），换栈的文档返工面已扫描确认：仅 **32 份文档**含技术栈表述，其中多数只是一行"技术栈"声明 + 底座模块的机制承载描述。

## 1. 变更动因（为什么现在换是对的）

### 1.1 选 PHP 的原始前提已消失

| 时点 | PHP 的理由 | 现状 |
|---|---|---|
| 决策建议书 V2 阶段 | 路径 A（Fork 商派）与路径 B（PHP 新架构）都基于"商派是 PHP，同栈可复用代码/团队经验" | **路径 B 已定不 fork**，商派代码降级为"参考实现"，只借鉴业务模型不抄代码——PHP 的复用价值归零 |
| 41 问 Q4 | Jason 曾选"沿用 PHP"（当时含"可直接复用商派代码"选项描述） | 路径 B 拍板后，"沿用 PHP"的实际含义已变成"用 PHP 从零写"，与"用 Python 从零写"工作量相当 |

**关键洞察**：Q4「沿用 PHP」和路径 B「新架构自研」组合后，PHP 已从"复用优势"退化为"纯语言选择"——此时应按团队技能与生态选，而非按商派历史选。

### 1.2 新增需求把天平推向 Python

| 需求（已拍板） | 语言相关性 | PHP 实现代价 | Python 实现 |
|---|---|---|---|
| **AI 销量预测**（G7，首期 M3 就要） | ML/时序预测生态 | 需跨语言调 Python 服务或 PHP-ML 弱生态 | 原生（scikit-learn/Prophet/statsmodels 同栈） |
| **K-AIDE Agent 接口**（Q41 预留） | LLM/Agent 生态 | 几乎全靠外部服务 | 原生（langchain/各 LLM SDK） |
| 规则引擎/条件 DSL | 通用 | 均可 | 均可（Python 动态性略优） |
| 数据 ETL/BI 供数（D11.02） | 数据处理 | 较弱 | 原生（pandas） |

AI 两项是 Jason 明确要"首期就要/预留"的，Python 同栈能省掉一层跨语言桥接（PHP 主服务 ↔ Python AI 服务的 RPC/序列化开销与运维复杂度）。

### 1.3 团队与招聘

- **团队主技能 = Python + Vue**（Jason 确认）：换栈后团队即刻可上手，M0 spike 无学习曲线
- **招聘市场**：Python + Vue 是全市场主流组合，招聘面远大于 PHP（尤其 Hyperf/Swoole 属 PHP 小众栈，会的人少）
- PHP 强项（快速出活、虚拟主机部署）对本项目（K8s 容器化、异步高并发、AI 集成）无优势

### 1.4 高并发指标 Python 能否扛住？（技术可行性）

Q37 定的性能指标：**审单 ≥500 单/分钟、库存同步 ≤10s、拉单 ≤1min**。

- 这些全是 **IO 密集型**（等 DB/Redis/MQ/平台 API），正是 FastAPI（asyncio + uvloop）的主场——单进程异步可撑数千并发 IO
- 核心防超卖机制 **Redis + Lua 原子预占**（D04.02/D04.03）**语言无关**：Lua 脚本跑在 Redis 里，Python 只是发起方，与 PHP 无差异
- 审单插件链、拆单策略是 **CPU 轻、IO 重**的规则编排，Python 异步完全够；真要压榨可用 uvloop + 多 worker（gunicorn/uvicorn workers）横向扩
- 结论：**中规模（日均 3千-2万单，Q9-Q12）FastAPI 无压力**；即便未来到大规模，异步栈 + 水平扩展路径清晰，不构成瓶颈

## 2. 新技术栈定案

### 2.1 后端

| 层 | 选型 | 说明 |
|---|---|---|
| Web 框架 | **FastAPI**（Python 3.11+） | 异步高吞吐；Pydantic 校验天然契合 canonical 标准模型与事件契约；自动 OpenAPI 文档（D02.07 对外网关省力） |
| ASGI 服务器 | uvicorn（+ gunicorn 多 worker 生产） | |
| ORM | **SQLAlchemy 2.0**（async） | 全域横切的数据权限中间件（D10.03）用 SQLAlchemy 事件/`with_loader_criteria` 实现行级过滤 |
| 迁移 | **Alembic** | 373 表 DDL 的版本化迁移（替代"直接执行 SQL"，研发期可控） |
| 校验/序列化 | **Pydantic v2** | canonical 模型、事件信封、API 契约的单一事实源 |
| 异步任务 | **Celery**（RabbitMQ broker）或 **arq**/dramatiq | MQ 消费 worker（D01.01 outbox 投递器、拉单、回传、审单批处理） |
| 定时调度 | **APScheduler** 或 Celery Beat | D01.02 统一调度器（商派 taskmgr 白名单声明式配置的 Python 等价） |
| 插件/规则 | **pluggy** 或自研责任链 + importlib 注册表 | D01.03 规则引擎、D03.02 审单插件链、D03.04 拆单 16 策略的承载 |
| 缓存/锁 | redis-py（+ Redis Lua） | 三元库存预占、分布式锁、幂等去重、热点缓存 |
| 可观测 | structlog + OpenTelemetry + Sentry | 对齐商派已有的 Sentry/日志规范 |

### 2.2 前端

| 层 | 选型 | 说明 |
|---|---|---|
| 框架 | **Vue 3 + TypeScript + Vite** | 团队主技能；组合式 API |
| 组件库 | **Element Plus** | 国内企业后台事实标准；审单工作台键盘流、大表格、表单开箱即用 |
| 状态 | Pinia | |
| 数据契约 | 后端 FastAPI 自动 OpenAPI → 前端 openapi-typescript 生成类型 | 前后端契约单一事实源，减少联调 |
| 多端 | 内部工作台（审单/客服360/运营）+ 品牌方门户（D10.04，可独立构建） | UI 业界主流风格（不强制 K-AIDE，Q39 决策）；门户可后续对齐 K-AIDE token |

### 2.3 不变的部分（强调：换栈不动地基）

- **数据库**：MySQL 8.0 不变；373 表 DDL、12 schema 划分、命名规范、公共字段、索引全部不变（DB-00 与各域字典零改动，仅个别"注解声明"表述微调）
- **中间件**：Redis 7 + RabbitMQ 不变
- **部署**：K8s 容器化不变（Python 容器镜像更轻）
- **全部业务契约**：五口径库存、三元记账键、货主维度、订单四套状态机、发货单指令状态机、191 领域事件字典——**一个都不动**
- **业务需求**：11 域 67 模块的功能范围、处理逻辑、验收标准不变

## 3. 商派机制 → Python 等价物映射表（研发参考核心）

需求文档大量引用"商派怎么做 + 凯淳怎么重写"。换栈后"重写"栏的 PHP 实现要翻译为 Python 等价物——**机制思想 100% 保留，只换技术载体**：

| 商派机制（PHP） | 凯淳原设计（PHP Hyperf） | **凯淳新设计（Python FastAPI）** | 涉及文档 |
|---|---|---|---|
| omeauto 审单插件链（PHP 类 + 位标记） | Hyperf 插件注册表 + 责任链 | **pluggy/自研责任链 + importlib 注册表**，插件=Python 类实现 `AuditPlugin` Protocol | D03.02/D01.03 |
| lib/split 16 拆单策略（策略模式） | Hyperf DI 标签注册策略 | **策略注册表（entry_points 或显式注册 dict）**，策略=纯函数/类 | D03.04/D01.03 |
| taskmgr 定时任务（Swoole 进程池 + whitelist.php） | Hyperf 常驻 Process + DI 标签 | **APScheduler/Celery Beat + 声明式任务注册表（Pydantic 配置）** | D01.02 |
| base 队列（Swoole 秒级队列） | RabbitMQ + Hyperf 常驻协程 worker | **RabbitMQ + Celery/arq worker（asyncio）** | D01.01 |
| dbschema PHP 数组定义表 + 注解 | PHP8 注解声明实体元数据 | **SQLAlchemy 声明式模型 + Pydantic Schema + 元数据注册表**（注解→装饰器/类属性） | D01.04 |
| dbevent 数据库事件钩子 | Hyperf 事件监听 | **SQLAlchemy ORM 事件（before/after_insert 等）+ 领域事件 outbox** | D01.01/各域 |
| services.xml 服务注册 | Hyperf DI 容器 | **Python DI（dependency-injector 或 FastAPI Depends）+ 模块注册表** | 全域 |
| Hyperf 中间件（脱敏/数据权限） | Hyperf middleware + ORM 全局 Scope | **FastAPI middleware/Depends + SQLAlchemy 事件全局过滤（with_loader_criteria）** | D01.05/D10.03 |
| Lua 规则脚本（ome/lua） | 保留 Lua（Redis 内执行） | **保留 Lua（Redis 内执行，语言无关）** | D04.02/D04.03 |
| Redis + Lua 预占 | 保留 | **保留（redis-py 调 Lua）** | D04.03 |
| erpapi 五层（签名/路由/报文/错误码/日志） | Hyperf 实现 | **FastAPI + httpx（异步 HTTP 客户端）+ 适配器抽象基类** | D02.01/D02.02 |
| 平台适配器 DI 标签注册 | `#[AdapterTag('taobao')]` | **适配器注册表（装饰器 `@register_adapter('taobao')` 或 entry_points）** | D02.02/D09.01 |

**要点**：Lua 脚本、Redis 预占、MQ 异步、事件驱动这些**核心机制与语言无关**，换栈零损失；变的只是"用什么语法写插件/注册服务/声明元数据"，都有成熟 Python 等价物。

## 5. 风险与回退

| 风险 | 等级 | 应对 |
|---|---|---|
| Python GIL 对 CPU 密集场景（如大批量审单计算）的影响 | 低 | 审单是 IO 密集非 CPU 密集；真 CPU 密集用多进程 worker 横向扩或 C 扩展；核心热点（库存预占）已在 Redis Lua，不经 Python |
| FastAPI 无自带 admin（Django 有） | 低 | 本项目前端全自建（Vue3 + Element Plus），不需要 admin；元数据 CRUD（D01.04）本就是自研通用渲染 |
| SQLAlchemy 异步 + 复杂查询的学习成本 | 低-中 | 团队 Python 主技能；M0 spike 验证数据权限全局过滤（D10.03）的 async 实现 |
| 已归档的 PHP 版文档与新栈不一致造成误解 | 中 | 本次全面修订 V2.0 + 决策留痕（本报告 + README §8 + 各文档变更记录）；腾讯文档云端同步更新 |
| Celery/APScheduler 选型细节 | 低 | M0 spike 期定型（与 FastAPI 一并验证），文档先写"MQ 异步任务框架"不锁死具体库 |

**回退**：技术栈是 M0 spike 前的决策，未写一行业务代码，**回退成本≈0**（改回文档表述即可）。这也是现在换而非研发中期换的最佳时机。
