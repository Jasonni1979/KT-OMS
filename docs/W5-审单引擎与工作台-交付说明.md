## 2. 核心机制（与商派的关键差异）

| 机制 | 商派做法 | 本方案 | 价值 |
|---|---|---|---|
| 审核原因 | `auto_status` 23 位位标记 | `ord_audit_reason` 结构化子表 | 可读/可检索/可统计（"本周地址类拦截 TOP 店铺"位标记做不到） |
| 决策与执行 | `_processConfirm` 决策即执行 | plan 落库先于执行，执行器异步消费 | plan 可重算、可回放（"为什么当时选了华东仓"可完整追溯） |
| 短路策略 | 逐插件 HOLD（审核员修一个冒一个） | ADMIT/WAREHOUSE/STOCK/LOGISTICS 短路，**CHECK 段不短路全收集** | 一次转人工带全问题清单 |
| 插件链 | 硬编码顺序 | 段 + 段内 order 的可插拔注册 | 新增插件不改引擎代码（AC-13） |
| 人工审核 | `mkDelivery` 独立第二执行路径 | 人工决策产 plan 走**同一执行器** | 消除双路径校验漂移隐患 |
| 规则模型 | 17 维 + weight DESC | 18 维（+货主）+ 显式 DSL + 快照 | 可解释 + 可回放 |

## 3. 本轮踩坑（已修，沉淀价值高）

1. **DDL 列名与 ORM 模型偏差（第三次同款坑）**
   - `ord_audit_reason` / `ord_audit_work_log` / `ord_audit_plugin_perf` / `ord_audit_batch_log` 是**追加型表**（只有 create_time，无 update_time/version/is_deleted）
   - `ord_audit_group` / `ord_dispatch_rule` **无 owner_id 列**
   - `ord_audit_work_log` 的 owner_id/task_id/op_id 是 **NOT NULL**（不是可空）
   - `inv_bom_item` / `inv_stock_ledger` **无 material_bn 列**（清理只能按外键子查）
   - `ord_order_item` 等子表**无 order_bn 列**（靠 order_id 关联）
   - **规律：每个新域的模型必须逐表 desc 核对 DDL，不能照抄其他域的基类**

2. **插件读 ctx.data，数据却放在 ctx.meta** → 地址校验恒判"区划缺失"
   - 框架契约：插件**只读数据袋**（ctx.data），元信息（session/候选集）在 ctx.meta
   - 修正：收货人只读字段进数据袋；密文地址用 `address_hash`/`address_len` 判「是否填写」（PIPL 下插件读不到明文）

3. **split_matrix 未带 bm_id** → 执行器预占拿不到物料 → STOCK_RACE
   - 拆单方案是**执行器的输入契约**，必须带齐行 ID + 数量 + 基础物料 ID + 货号

4. **`task_limit=0` 被 `or DEFAULT` 覆盖** → 满载判断失效
   - 显式 0 表示「不接受任何任务」，不能用 `or` 兜默认值

5. **测试硬编码 owner_id=5** → CI 空库与开发库 ID 不同 → 用例在 CI 失败
   - 测试必须**查实际存在的货主**，不能硬编码主键

6. **CI 复演库缺 seed_audit** → 审单链无候选仓/物流 → 场景与用例路径与开发库不一致
   - 已把 seed_audit 加入 `deploy/ci-local-rehearsal.sh`

7. **FastAPI 新版 `include_router` 延迟挂载** → `app.routes` 看不到子路由
   - 验证路由要用 `openapi.json`，不能直接遍历 `app.routes`

8. **方法名 `list` 遮蔽内置 list 类型** → mypy valid-type 报错（第二次同款坑）
   - 服务层统一用 `list_items` / `list_plugins`
