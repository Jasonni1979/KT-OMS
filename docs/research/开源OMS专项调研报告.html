开源 OMS 专项调研
面向电商代运营 + 经销双业务场景

聚焦国内开源项目，服务两类业务：代运营（多品牌多店铺、平台授权、货权分离、三方结算）与 经销（采购入库、成本核算、多仓调拨、批发价格体系）。 协议全量收录不做预过滤，含 MIT / Apache-2.0 / AGPL-3.0 / GPL-3.0 / 自定义等。

数据来源：GitHub REST API 实测 候选项目：12 个逐一核验 核验时间：2026-10-17 WMS 部分另行调研

1核心结论

结论 1：国内开源 OMS 的协议分布高度集中于 AGPL-3.0 与 Apache-2.0，纯 MIT 的可用项为零

12 个候选中，功能最贴合电商代运营/经销场景的两个项目——zeasin/qihang-erp-open（启航 ERP，平台覆盖最广） 与 lilishop/lilishop（B2B2C 多商户）——均为 AGPL-3.0。 真正协议干净的只有 ShopeX/OMS（商派 ONEX OMS，Apache-2.0），且它的业务完整度恰恰最高。

结论 2：ShopeX ONEX OMS 是唯一「协议干净 + 业务完整 + 厂商级迭代」三重达标项

商派（ShopEx）官方开源，Apache-2.0，v8.10.0 于 2026-09-26 发版。 代码库含 60+ 个业务模块，其中 taoguan*（淘宝官仓）、dealer（经销商）、 presale（预售）、vop（京东 VOP）、o2o/pos（线上线下）、 tgstockcost（库存成本）、purchase（采购）、finance（财务） —— 这些模块名直接对应代运营与经销的核心诉求，与通天晓 OFS 的业务模型重合度最高。

结论 3：启航系（qihang）是「功能陷阱」——平台覆盖最广，但协议是 AGPL-3.0

zeasin/qihang-erp-open 支持淘宝天猫、京东、拼多多、抖店、微信小店、快手、小红书全平台， 还有多商户架构、京东云仓对接、Spring AI 2.0 原生集成——功能诱惑极大。 但 AGPL-3.0 下，只要通过网络提供服务就必须开放全部修改后源码， 对闭源商用是硬性排除项，只可作产品需求参考，不可作代码底座。

结论 4：同一作者不同协议，说明这是刻意的开源商业模式设计

值得注意的细节：zeasin/qihang-cb-erp（跨境电商版，支持 idosell / Shein）用的是 Apache-2.0，而国内版 zeasin/qihang-erp-open 用的是 AGPL-3.0。 这不是疏漏，而是典型的开源核心（open-core）商业策略：用宽松协议做海外市场获客，用传染协议锁住国内主流市场。 引用其代码前需格外警惕协议边界。

⚠ 关键提示：AGPL-3.0 在电商场景的触发条件比想象中更容易满足

AGPL-的传染判定不看「是否分发软件」，而看「是否让用户通过网络与之交互」。 这意味着：只要把启航 ERP 部署到内网给运营团队用，就已经构成网络交互， 即便一个客户都没接入，也有向使用者开放源码的义务。不存在"内部使用所以没事"的灰色地带。

对"原诉求 MIT 协议"的回应

在 OMS 领域，纯 MIT 的可用项目为零（仅存的 MIT 项是 0 star 个人分叉）。 建议将法务准入标准调整为 Apache-2.0：它同样允许闭源商用与修改， 且比 MIT 多了专利授权与专利反诉终止条款——对"规避知识产权风险"这一原始目标，保护力度实际更强。 按此标准，ShopeX/OMS 是唯一同时满足协议与业务完整度的选项。

8落地路径建议

1

法务前置：把准入标准从 MIT 调整为 Apache-2.0

OMS 领域纯 MIT 可用项为零。Apache-2.0 同为宽松许可，且额外提供专利授权与反诉终止保护。这一步不通过，后面全部作废。

2

沙箱 PoC：ShopeX ONEX OMS 导入真实历史订单

重点验证 taoguan*（淘宝官仓）、dealer（经销）、presale（预售）、tgstockcost（成本核算）四个模块是否与通天晓 OFS 现有流程对得上。用 Docker 部署，一周内可出结论。

3

平台适配层自建，参考启航与 openlinker

把电商平台对接抽成独立适配层（每平台一个 adapter），主体不动。启航的平台覆盖最广（7 平台），openlinker 是 API-first 架构参考。这层必须是自有的，避免被任何上游协议绑定。

4

双轨并行，按渠道增量切换

通天晓 OFS 不立即下线。新渠道、新品牌店铺先走新 OMS，通过库存同步管道与通天晓对齐。任一渠道出问题可秒级回退。

5

核心资产自有化

订单状态机、库存五态口径、寻源/分单规则、结算分账模型——这四块必须完全自有，不依赖任何上游仓库的开源更新节奏。

9立即执行的合规排查

⚠ 请技术团队今日内确认
  • 排查内部是否已 clone 或引用启航系仓库（qihang-erp-open、qihang-oms、lilishop）。AGPL-3.0 项目一旦进入内网部署即触发开源义务，越早移除越好。
  • 排查 kingchang/oms-erp：Apache-2.0 但 0 star、停滞 28 个月、仓库实际为空壳。若已被当作"开源中台"引入，需立即停止。
  • 记录 ShopeX/OMS 的 NOTICE 与 LICENSE 文件：Apache-2.0 要求保留版权声明与 NOTICE，商用分发时不可删除。
一句话总结

OMS 侧的唯一可行答案是 ShopeX ONEX OMS（Apache-2.0）——它协议干净、业务完整度最高、 有厂商级迭代，且 taoguan* / dealer / presale / tgstockcost 这些模块就是照着代运营和经销画的。 代价是 PHP 技术栈与微信小店/快手/小红书的对接缺口，前者需评估团队适配成本，后者用自建适配层补。 启航系功能更全但 AGPL-3.0，只能当需求文档读，不能当代码用。
