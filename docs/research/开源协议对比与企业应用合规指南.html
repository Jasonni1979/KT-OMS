1先理解三个判断维度

所有开源协议的差异，最终都可以归结为三个问题的不同答案。搞清这三件事，整张表就不用死记。

1

能不能闭源商用？（Permissive vs Copyleft）

宽松许可（MIT / Apache / BSD）只要求你保留版权声明，改造后可以完全闭源、随便卖。著佐权（Copyleft）则要求衍生作品保持同一协议——GPL 系要求整体开源，AGPL 更进一步。

2

传染范围有多大？（Scope）

这是最容易被忽略、也最关键的一点。同样是 Copyleft，边界完全不同：文件级（MPL，只污染改过的文件）、模块级（EPL）、库级（LGPL，只污染那个库）、整体级（GPL，污染整个组合作品）。

3

什么动作会触发义务？（Trigger）

分发（把软件交给别人）才会触发 GPL；网络交互就会触发 AGPL——这是绝大多数企业踩坑的地方。很多人误以为"SaaS 不分发所以没事"，这只对 GPL 成立，对 AGPL 完全不成立。

⚠ 企业场景最常犯的三个认知错误
  • "内部部署使用，不分发，所以 GPL/AGPL 没事" —— 错。AGPL 第 13 条的触发条件是"让用户通过网络与之交互"，内网部署给员工用就已经构成网络交互。GPL 确实不因内网使用触发，但只要你把系统交付给客户（哪怕是以 SaaS 形式），就要重新审视。
  • "我只调用它的 API / 只作为独立进程运行，不算衍生" —— 这是灰色地带，争议极大。FSF 立场认为同进程内的动态链接即构成衍生作品；业界普遍接受"独立进程 + 标准 IPC"更安全。商业项目不要赌这个边界。
  • "协议是 MIT/Apache，所以怎么用都行" —— 宽松许可确实允许闭源，但必须保留版权声明与许可文本，Apache-2.0 还要求保留 NOTICE 文件并声明你做过修改。漏掉这些同样是违约。

2四大协议家族

① 宽松许可
Permissive

只要求保留版权声明与许可文本，改造后可以闭源商用。对企业最友好，无需开源自身代码。

  • MIT — 最短最宽松，无专利条款
  • Apache-2.0 — 宽松 + 专利授权 + 反诉终止
  • BSD-2/3-Clause — 类似 MIT，3-Clause 多禁背书条款
  • ISC — 功能同 MIT，措辞更短

适用：企业自研产品底座、对外分发的商业软件。

② 弱著佐权
Weak / File-level Copyleft

Copyleft 只覆盖被修改的那个文件/模块/库，你自己写的代码可以保持闭源。需做架构隔离。

  • MPL-2.0 — 文件级，GPL 兼容（条款 3.3）
  • EPL-1.0 / EPL-2.0 — 模块级，2.0 可选 GPL 兼容
  • LGPL-2.1 / 3.0 — 库级，用户须可替换该库

适用：基础库、中间件；要求工程上做清晰的文件/模块边界。

③ 强著佐权
Strong / Network Copyleft

衍生作品整体必须保持同协议并开源。与闭源商用目标直接冲突。

  • GPL-2.0 / 3.0 — 分发即触发，整体开源
  • AGPL-3.0 — 网络交互即触发，SaaS 杀手
  • SSPL-1.0 — 更狠，连服务端基础设施都要开源

适用：纯开源项目、可公开源码的内部系统。闭源商用须排除。

④ 伪开源 / 源码可见
Source-Available（非 OSI 认可）

名字带 License、源码可见，但含商业限制条款，不属开源。法务上按专有软件处理。

  • SSPL-1.0 — 未被 OSI 批准
  • BUSL-1.1 — 限时，到期转开源
  • Elastic-2.0 — 禁提供托管服务
  • Commons Clause — 附加在开源协议上的限制条款

适用：基本不适用。见到应直接视为专有软件 + 商业谈判。

很多人只盯着"能不能闭源商用"，但真正的决策依据是触发条件 × 传染范围： GPL 虽然整体传染，但只要你不分发软件就有操作空间；AGPL 连这个空间都没有。 反过来，MPL/EPL 虽然也是 Copyleft，但只污染改动部分，通过工程隔离完全可以安全商用。

4逐协议详解

4.1 宽松许可（企业最友好）

MITMassachusetts Institute of Technology License · 最短最宽松宽松
含义：全称麻省理工学院许可证，全文仅百余词。核心就一句话——保留版权声明和许可声明，你可以任意使用、复制、修改、合并、发布、分发、再授权、销售。
✅ 允许
  • 商业使用、闭源分发、售卖
  • 修改后闭源，无需开源任何代码
  • 再授权为其他协议（含专有协议）
  • 无 copyleft、无网络条款
⚠️ 约束
  • 必须保留原版权声明与许可文本
  • 无明示专利授权条款——贡献者专利不受书面保护
  • 不提供任何担保，出问题自担
企业注意：MIT 是"最低门槛"，但因为缺专利条款，理论上存在贡献者专利主张风险。大规模商用重要组件时，Apache-2.0 是更稳的选择。
Apache-2.0Apache Software Foundation · 宽松 + 专利保护宽松
含义：Apache 软件基金会推出的宽松许可。保留 MIT 式的自由，额外加入明示专利授权与专利反诉终止机制。
✅ 允许
  • 商业使用、闭源分发、售卖、改协议
  • 修改后完全闭源
  • 贡献者明确授予专利许可（覆盖其贡献所涉专利）
  • 与 GPL-3.0 兼容（可与 GPL-3.0 代码合并）
⚠️ 约束
  • 保留版权声明、许可文本 + NOTICE 文件
  • 必须声明你做过修改（modified files notice）
  • 专利反诉终止：你若因该软件发起专利诉讼，授权自动终止
  • 与 GPL-2.0-only 不兼容
  • 不得使用 Apache 商标做背书
企业注意：这是企业开源项目的首选协议。相比 MIT 多出的专利授权 + 反诉终止条款，对"规避知识产权风险"的目标保护力度实际强于 MIT。代价是合规动作更多（NOTICE + 修改声明）。
BSD-2 / BSD-3-ClauseBerkeley Software Distribution · MIT 的近亲宽松
含义：加州大学伯克利分校发布的宽松许可。BSD-2-Clause 功能上等同 MIT（保留声明即可）。BSD-3-Clause 多一条：不得用原作者名义为衍生产品背书。
✅ 允许
  • 商业使用、闭源、改协议、售卖
  • 无 copyleft、无网络条款
⚠️ 约束
  • 保留版权声明与免责声明
  • 3-Clause 额外禁止使用作者名做宣传背书
  • 无专利条款（同 MIT）
企业注意：与 MIT 实质等价，选型时无需区分。BSD-3 的禁背书条款在营销合规上有实际意义。

4.2 弱著佐权（可用，但需架构隔离）

MPL-2.0Mozilla Public License · 文件级 Copyleft弱著佐权
含义：Mozilla 推出的弱著佐权许可。Copyleft 只覆盖被修改的那个源文件——MPL 文件改了就得以 MPL 发布，但你新增的文件可用任意协议（含闭源）。
✅ 允许
  • 商业使用、闭源分发自有代码
  • 与专有代码混合在同一项目
  • 含专利授权条款
  • 与 GPL v2/v3、LGPL 兼容（条款 3.3 次级许可机制）
⚠️ 约束
  • 修改过的 MPL 文件必须以 MPL 开源
  • 必须保留版权与许可信息
  • 不要把 MPL 代码片段复制粘贴进自己的文件——会扩大污染面
  • 文件头需标注"Incompatible With Secondary Licenses"否则自动兼容
企业注意：MPL 是"可安全商用的 Copyleft"，前提是工程上保持文件边界清晰。典型用户：Firefox、Thunderbird。
EPL-1.0 / EPL-2.0Eclipse Public License · 模块级 Copyleft弱著佐权
含义：Eclipse 基金会的弱著佐权许可。Copyleft 在模块/组件级别——修改的 EPL 模块须以 EPL 发布，但独立模块可专有。EPL-2.0 新增 Secondary License 机制可指定 GPL-2.0 为次级许可以解决 GPL 兼容问题。
✅ 允许
  • 商业使用、与专有代码组合分发
  • 含专利授权 + 专利反诉条款
  • EPL-2.0 可通过次级许可实现 GPL 兼容
⚠️ 约束
  • 修改的 EPL 模块须开源
  • 须明确声明哪些模块是 EPL、哪些不是
  • EPL-1.0 与 GPL 不兼容（1.0 无次级许可机制）
  • IBM/Eclipse 生态为主，跨生态项目少见
企业注意：本次 WMS 调研中的 openboxes/openboxes 即为 EPL-1.0。注意 1.0 与 2.0 的关键差别：1.0 无 GPL 兼容路径，且 Copyleft 边界为"模块"，隔离成本略高于 MPL 的"文件"。
LGPL-2.1 / LGPL-3.0Lesser GPL · 库级 Copyleft弱著佐权
含义：GPL 的"弱化版"，专为函数库设计。Copyleft 只作用于那个库本身——链接它的应用可以闭源，但用户必须能替换该库。
✅ 允许
  • 闭源应用链接 LGPL 库并商业分发
  • 动态链接最简单（用户替换 .so/.dll 即可）
  • LGPL-3.0 含专利授权
⚠️ 约束
  • 库本身及其修改必须开源
  • 用户必须能替换该库（可替换性要求）
  • 静态链接须提供目标文件（.o）或源码，允许重新链接
  • 移动端 App Store 分发需格外小心（安装信息要求）
  • 头文件定义的数据结构是否传染存在争议
企业注意：LGPL 在服务端动态链接场景基本安全；静态链接、嵌入式、App Store 是三个高风险场景，须提前做合规设计。

4.3 强著佐权（闭源商用须排除）

GPL-2.0 / GPL-3.0GNU General Public License · 整体传染强著佐权
含义：自由软件基金会推出的强著佐权许可。衍生作品整体必须保持 GPL 并提供完整源码。GPL-3.0 额外加入专利授权、反 Tivo 化、兼容 Apache-2.0。
✅ 允许
  • 商业使用、收费分发（但必须同时开源）
  • 纯内部使用且不分发，无开源义务
  • GPL-3.0 含明示专利授权
⚠️ 约束
  • 分发衍生作品时必须提供完整对应源码
  • 与闭源代码同进程链接即可能整体污染
  • GPL-2.0-only 与 Apache-2.0 不兼容
  • 触发条件是"分发"，纯 SaaS 不触发（这是唯一操作空间）
企业注意：本次 WMS 调研中的 erzhongxmu/JeeWMS（OMS+WMS+BMS+TMS 四合一）即 GPL-3.0。它与 Apache-2.0 的 OMS 组合会导致整体被迫开源——这是本次调研识别的最高优先级协议风险。
AGPL-3.0Affero GPL · GPL + 网络条款（企业最大陷阱）网络著佐权
含义：GPL-3.0 加第 13 条"远程网络交互"条款。即使用户只是通过网络访问你的服务、你完全没有"分发"软件，也触发开源义务。这是 AGPL 与 GPL 的唯一实质差别，也是它最危险的地方。
✅ 允许
  • 商业使用、收费（但须同时开源）
  • 完全不开放给外部使用的纯离线场景
  • 含 GPL-3.0 全部专利保护
⚠️ 约束
  • 网络交互即触发，无"内部使用"灰色地带
  • 衍生作品整体必须开源
  • 内网部署给员工用同样构成网络交互
  • 与 Apache-2.0 组合会污染整个项目
企业注意：本次 OMS 调研中的 zeasin/qihang-erp-open（启航电商 ERP，平台覆盖最广、功能最全）与 lilishop/lilishop（★4327）均为 AGPL-3.0。它们功能最诱人，但对企业闭源商用是硬性排除项——只能作产品需求参考，不可作代码底座。

4.4 源码可见但非开源（按专有软件对待）

SSPL-1.0Server Side Public License · MongoDB 2018 推出源码可见
含义：基于 GPL-3.0 改写第 13 条。提供软件即服务时，不仅要开源该软件，还要开源整个服务栈——管理软件、API、自动化、监控、备份、存储、托管等全部。
✅ 允许
  • 自由使用、审查、修改、再分发源码
  • 非服务场景（如内部工具）相对宽松
⚠️ 约束
  • 未被 OSI 认可为开源（2019 年被拒）
  • 提供服务须开源整个服务基础设施
  • Debian、RHEL、Fedora 已将其从发行版中移除
  • Red Hat / Debian / FSF 均认定其不自由
企业注意：见到 SSPL 直接按专有软件 + 商业谈判处理，不要走开源合规流程。典型用户：MongoDB（2018-10-16 起）、Graylog 4.0+、Redis 7.x（2024-2025 期间）。
BUSL-1.1 / Elastic-2.0限时或限场景的源码可见协议源码可见
含义：BUSL（Business Source License）限时——生产使用受附加条款限制，到期（不超过 4 年）转为指定开源协议。Elastic License 2.0——不得作为托管服务提供、不得绕过许可密钥。
✅ 允许
  • 查看、修改、内部使用源码
  • BUSL 到期后自动转为开源协议
⚠️ 约束
  • 均未被 OSI 认可
  • BUSL 生产使用受限，需逐项目读"Additional Use Grant"
  • Elastic-2.0 禁止提供托管服务
  • 每个项目的附加条款不同，无法统一判断
企业注意：这类协议没有通用判断标准，必须逐项目读附加条款。典型用户：MariaDB、CockroachDB（BUSL）、Elasticsearch / Kibana 7.8+（Elastic-2.0 + SSPL 双许可）。

5组合兼容性矩阵

自研系统往往是"多个开源组件 + 自有代码"的组合。关键问题：这些协议混在一起后，整体能否保持闭源？

组合方式可否闭源商用原因与注意点
MIT + Apache-2.0 + BSD + 自有代码 ✅ 完全可行 宽松许可之间可自由组合。仅需保留全部版权声明 + Apache 的 NOTICE 与修改声明。整体可闭源、可售卖。
Apache-2.0 + Apache-2.0
（如 ShopeX OMS + GreaterWMS）		 ✅ 完全可行 本次推荐组合正是此结构。双 Apache-2.0 无任何冲突，各自保留 NOTICE / LICENSE 即可整体闭源商用。
MPL-2.0 + 自有代码 ✅ 可行 自有文件保持闭源。前提：不要把 MPL 代码复制进自有文件，保持文件边界。
EPL-1.0 + 自有代码 ⚠️ 需架构隔离 修改的 EPL 模块须开源。须清晰划分模块边界，并注意 EPL-1.0 与 GPL 无兼容路径。
LGPL 库 + 自有闭源应用 ⚠️ 有条件可行 动态链接安全；静态链接须提供目标文件允许重链；App Store 分发须额外处理。
GPL-3.0 + Apache-2.0 组合 ❌ 不可闭源 GPL-3.0 虽与 Apache-2.0 协议兼容，但组合结果整体按 GPL-3.0 处理，必须开源。这就是 JeeWMS + ShopeX OMS 的风险。
AGPL-3.0 + 任意闭源代码 ❌ 不可闭源 网络交互即触发整体开源。哪怕只是内部署一个 Web 服务，也无灰色地带。这是最严格的组合。
GPL-2.0-only + Apache-2.0 ❌ 协议不兼容 Apache-2.0 的专利/修改条款与 GPL-2.0 冲突，法律上不允许合并分发。GPL-3.0 才兼容 Apache-2.0。
SSPL + 自有代码（提供服务时） ❌ 不可行 须开源整个服务栈含基础设施。直接按专有软件谈判处理，勿走开源流程。
自定义 / NOASSERTION + 任意 ⚠️ 不可判定 协议不明即视为有风险。须先取得明确许可文本并由法务出具意见，否则不进入 PoC。
✅ 本次 OMS / WMS 选型的协议结论

ShopeX ONEX OMS（Apache-2.0）+ GreaterWMS 2.x（Apache-2.0）落在表格第二行—— 双宽松许可组合，整体可闭源商用，无任何协议冲突，合规动作仅是保留双方的 NOTICE 与 LICENSE 文件、声明修改。 这是本次调研在协议层面能给出的最好结果。

7企业落地检查清单

7.1 选型前必问（按此顺序）

1

我们要不要闭源？

要闭源 → 只考虑宽松许可（MIT / Apache-2.0 / BSD）与弱著佐权（MPL / EPL / LGPL，需隔离）。强著佐权（GPL / AGPL / SSPL）直接出局，除非公司战略就是开源。

2

软件会以什么形式交付？

分发给客户 → GPL 会触发，须评估。只做 SaaS → GPL 不触发（唯一操作空间），但 AGPL / SSPL 照样触发。内网自用 → AGPL 仍触发。

3

协议传染边界在哪里？

确认是文件级（MPL）/ 模块级（EPL）/ 库级（LGPL）/ 整体级（GPL）。然后检查工程上能否维持这个边界——这是弱著佐权能否安全商用的关键。

4

协议文本是否明确？

NOASSERTION / 自定义协议 / 空 LICENSE 文件 = 视为有风险。必须先取得明确许可文本并由法务出具书面意见，否则不进入 PoC。本次 wms2/mywms 即属此类。

7.2 已确定采用后的合规动作

协议必须做的事常见遗漏点
MIT / BSD / ISC在所有副本中保留版权声明与许可文本重构代码时把注释里的版权头删掉了
Apache-2.0保留版权声明 + NOTICE 文件 + 在修改过的文件中声明修改NOTICE 文件最容易漏；"声明修改"也常被忽略
MPL-2.0改过的 MPL 文件以 MPL 开源 + 保留声明复制粘贴 MPL 代码进自有文件，扩大污染面
EPL修改的模块以 EPL 开源 + 明确标注模块归属没在文档里说清哪些模块是 EPL
LGPL库本身开源 + 保证用户可替换（动态链接优先）静态链接时没提供目标文件；移动端商店限制
GPL / AGPL衍生作品整体开源 + 提供完整对应源码以为"内网/SaaS 不分发就没事"（AGPL 不成立）

7.3 给凯淳本次选型的一句话结论

协议层面的最终建议

如果法务原本的硬性要求是 MIT，需要重新审视：在 OMS / WMS 领域，MIT 几乎没有成熟可选项目 （仅存的是 0 star 个人分叉）。而 Apache-2.0 同属宽松许可，允许闭源商用、修改、再分发， 且额外提供明示专利授权与专利反诉终止保护——对"规避知识产权风险"这个原始目标，保护力度实际强于 MIT。

按 Apache-2.0 作准入标准，本次选型得到最优解：ShopeX ONEX OMS + GreaterWMS 2.x，双 Apache-2.0 组合，整体可闭源商用。 同时必须书面排除 JeeWMS（GPL-3.0）与启航系（AGPL-3.0），并在团队内明确： 这两个项目功能再全也不能进代码库，只能当产品需求文档读。
