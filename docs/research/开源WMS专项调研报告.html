开源 WMS 专项调研
与 ShopeX ONEX OMS 的组合可行性

承接 OMS 调研结论（已选定 ShopeX ONEX OMS，Apache-2.0 / PHP）， 本次聚焦国内 WMS 开源项目，协议全量收录不预过滤， 并重点评估 OMS + WMS 组合方案的整体可行性——包括协议兼容性、接口标准、技术栈协同与实施风险。

1核心结论

结论 1：组合方案成立，且协议层面完全兼容

OMS 侧已选定 ShopeX/OMS（Apache-2.0），WMS 侧首选 GreaterWMS（Apache-2.0）。 两者同为 Apache-2.0，协议层面无冲突，组合后仍可整体闭源商用， 且各自保留 NOTICE / LICENSE 即可满足合规要求。这是本次调研最重要的结论。

结论 2：接口标准已经现成——奇门（Qimen）是打通两侧的钥匙

ShopeX ONEX OMS 代码库内含 qimen（奇门）、wms、wmsmgr、omevirtualwms、ediws 五个与 WMS 对接相关的模块。奇门是国内电商生态（淘宝/京东）事实标准的仓储对接协议， 这意味着 OMS 侧天生具备对接标准化 WMS 的能力，无需自研接口协议—— 只要能找到支持奇门的 WMS，或给 WMS 加一层奇门适配器即可。

结论 3：WMS 侧没有"开箱即用"的选项，全部需要自建对接层与能力补齐

与 OMS 侧（ShopeX 业务完整度高）不同，WMS 侧所有候选都存在明确缺口： GreaterWMS 缺多货主隔离与奇门对接、JeeWMS 是 GPL-3.0、MT-WMS 体量过小、 cangmishu 停滞在 2021 年。WMS 是这次替换中真正需要投入研发的主战场，不是挑个开源项目部署就能用的。

结论 4：警惕 GreaterWMS 的 3.0 重构风险

GreaterWMS README 宣称 3.0 已用 Bomiot（宣称"Rust 插件架构"）完整重构， 但实测：公开分支（master / new / gh-pages）仍全部是 Django 2.x 结构， 最新 Release 也仍是 V2.1.52（2026-09-15）。 而 Bomiot 项目本身仅 22 stars，且实际定位是"Python 免环境交付工具"（编译二进制 / 源码保护）， 并非 README 宣称的 Rust 框架。这意味着 4411 star 的成熟度属于 2.x， 而 3.0 是一次未经验证的重构——采用时必须锁定 2.x 分支，不追 3.0。

组合方案总结

协议和接口标准两层已经打通，这是最大的好消息。 但在"多货主隔离""库存口径对齐""FEFO 批次效期"三个电商仓储核心能力上， 开源 WMS 均不能提供开箱即用的答案——这三块必须自研。 因此组合方案的正确定位是：OMS 用 ShopeX 拿业务完整度，WMS 用开源项目拿起步速度，核心仓储能力自建。

5协议合规性分析

B 档 待确认 NOASSERTION ⚠️ 需法务确认 wms2/mywms ⚠️ 协议文本需单独审查

与 Apache-2.0 的 OMS 混用会导致整体被迫开源
⚠ 特别注意：JeeWMS 是本次最大的协议陷阱

erzhongxmu/JeeWMS 把 OMS + WMS + BMS + TMS 四合一做在一套 Java 系统里， 功能看起来"一步到位替换通天晓全家桶"，且维护活跃（2026-10-09 仍有提交）、代码量 108MB。 但它是 GPL-3.0——一旦引入，会与已选定的 Apache-2.0 OMS 产生协议污染： GPL 的传染性会沿着"链接/组合"边界扩散，最终导致整个 OMS+WMS 组合被迫开源。 这是比"功能不全"严重得多的风险，必须排除。 它的正确用法：作为 WMS 业务需求与流程设计的参考实现（波次规则、PDA 作业流、费用结算链路），不作代码底座。

wms2/mywms 的协议疑点

wms2/mywms 的 license.spdx_id 为 NOASSERTION，且 COPYING 文件内容为空。 该项目源自德国的 myWMS LOS（社区版通常为 GPL），协议状态不明即视为有风险。 若考虑采用，须先取得明确的许可证文本并由法务出具意见，否则不建议进入 PoC。

7推荐组合与落地路径

最终推荐组合

ShopeX ONEX OMS（Apache-2.0 / PHP）　+　GreaterWMS 2.x（Apache-2.0 / Django）　+　自建三层核心能力

  • 自建层 1 · 多货主权模型：OMS 侧货主模型向 WMS 侧延伸，实现一仓多货主 / 一货主多仓的数据隔离
  • 自建层 2 · 库存口径对齐：把 OMS 五态口径（实际/可用/锁定/在途/次品）在 WMS 侧落地，防超卖
  • 自建层 3 · FEFO 批次效期 + 奇门适配：美妆个护行业硬约束 + 与 ShopeX qimen 模块的标准对接

七阶段推进路径

1

法务确认（1 周）

确认 Apache-2.0 组合方案可用，明确 NOTICE / LICENSE 保留要求。同时书面排除 JeeWMS（GPL-3.0）与启航系（AGPL-3.0），避免团队误引入。

2

接口方案设计（2–3 周）

基于 ShopeX 的 qimen 模块设计 OMS↔WMS 对接规范：订单下发、库存回传、发货回告、取消拦截四类主流程。先定协议再动代码。

3

双沙箱并行部署（2 周）

ShopeX OMS 与 GreaterWMS 2.x 各自 Docker 部署，锁定 V2.1.52 tag，禁用 3.0 分支。用脱敏历史订单联调主流程。

4

三大自建层攻坚（6–10 周）

多货主权模型、库存五态对齐、FEFO + 奇门适配。这是整个项目研发投入最集中的阶段，建议由最资深的工程师主导，并配套完整的单元测试与对账机制。

5

单仓单渠道试点（4–6 周）

选一个仓、一个渠道（建议先非核心渠道）跑真实业务。与通天晓 WMS 双轨并行，每日库存对账，验证账实相符率。

6

灰度扩量（持续）

按仓 → 按渠道 → 按品牌逐步切换。每扩一级都必须通过对账指标门槛（建议库存差异率 < 0.1%、发货差错率 < 万分之三）才继续。

7

能力内化与上游解耦

把对 GreaterWMS 的依赖收敛到"仓储作业执行层"，核心的货主/库存/效期/接口逻辑全部自有。上游停更时可原地接管，这是自研路线能否成立的关键。

8风险清单与立即排查项

⚠ 请技术团队今日内确认
  • 排查是否已引入 JeeWMS：GPL-3.0，与 Apache-2.0 的 OMS 组合会导致整体被迫开源。这是本次调研识别的最高优先级协议风险。
  • 排查 zhuoshao/Y-oms-wms-tms-bms：GPL-3.0 且是 2022 年的历史代码转储（0 star、无维护）。README 详尽易误判为成熟项目。
  • 确认 GreaterWMS 采用版本：必须锁定 V2.1.52 或同代 2.x tag。README 宣称的 3.0（Bomiot 重构）在公开分支中不存在，Bomiot 本体仅 22 stars，不可作为生产依赖。
  • 确认 wms2/mywms 协议：COPYING 文件为空、SPDX 为 NOASSERTION，协议不明即视为有风险，进入 PoC 前须取得明确许可文本。

组合方案整体风险

🧬

技术栈双轨成本

OMS（PHP）+ WMS（Python/Django）需两套技术栈团队。若强行统一到 PHP，唯一同栈候选 cangmishu 已停滞 5 年。

建议：接受异构，用接口标准化而非技术栈统一来降低复杂度。

📦

三大能力缺口

多货主隔离、库存五态对齐、FEFO 效期硬约束——这三项目前开源侧均无成熟答案，合计预估 2–3 人 × 6–10 周投入。

🔭

上游路线图风险

GreaterWMS 作者在 README 明确推介 3.0（Bomiot 重构），但公开分支仍是 2.x。存在"社区重心转移、2.x 事实上冻结"的可能，需每季度复核 Release 节奏。

🏭

自动化设备长期缺口

仅 openwms 有 MFC 概念。若未来引入 AGV / 分拣线，需规划 WCS 中间件——这部分通天晓的经验无法从开源继承。

一句话总结

组合方案可行，且协议层已经打通（双 Apache-2.0，可整体闭源）——这是本次调研最大的好消息。 接口标准也现成（ShopeX 自带 qimen 模块）。 但要清醒：WMS 侧没有"挑一个部署就能用"的选项，多货主、库存口径、FEFO 三大缺口必须自建， 同时必须锁定 GreaterWMS 2.x、书面排除 JeeWMS（GPL-3.0）。 务实定位：OMS 借 ShopeX 拿业务完整度，WMS 借 GreaterWMS 拿起步速度，核心仓储能力自建。
