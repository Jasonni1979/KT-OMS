阶段 3 · 技术路线决策

自研 OMS「沿用 PHP」三条路径
Fork 商派 vs 新架构自研 vs 混合 · 代码取证对比

基于对 ShopeX/OMS 源码的第二轮定向取证（矩阵中心耦合面、平台适配完整性、erpapi↔ome 耦合度、框架依赖）， 对 Q4「沿用 PHP」的三条实施路径做工作量、风险与团队要求的量化对比，供决策。

取证基线：main @ 2026-10-21 团队：4-6 人 规模：日均 3千-2万单 平台：淘/京/抖/拼/红/唯 6 家

0摘要与推荐

推荐：路径 B —— PHP 新架构自研（Hyperf 或 Laravel），商派代码降级为「参考实现」

决定性理由：① 取证证实开源商派的平台对接层无法独立使用——所有平台 API 硬编码走商派矩阵中心（matrix-gw-open.shopex.cn）+ license 证书认证，且不含抖音适配（0 个文件）。平台对接这个最大成本块（4-6 人月）三条路径都省不掉，Fork 的核心卖点失效。② 我们的两个地基需求（货主维度三元库存、多租户门户）在商派单货主大内核上属于「在已建好的楼上打地基」，改造风险高于按三元模型重新设计。③ Fork 最大的价值——不用从零理解业务——已经通过 6 份逆向文档兑现了。

例外：若上线时间压力 < 4 个月，选路径 A（Fork + 改造 + 采购商派矩阵服务）

A 是唯一能在 3-4 个月出可用系统的路线，但前提是接受：向商派采购矩阵中心商业服务（数据过商派服务器、按年付费）、抖音适配自行开发、货主维度改造在 113 万行历史代码上进行。本质上是「用长期技术债和供应商锁定换上线速度」——与公司既定的自研决策方向相悖，只建议作为时间倒逼下的备选。

1代码取证：4 个决定性事实

事实 1开源版的平台对接是「半截子」：报文映射在仓库里，签名与传输在商派的 SaaS 网关里

erpapi 的 76 个平台目录（645 个映射文件）只做「OMS 内部字段 ↔ 平台报文字段」的翻译；真正的 HTTP 出口硬编码为 MATRIX_URL = 'https://matrix-gw-open.shopex.cn/'，每次调用携带 certi_id（商派 license 证书）签名后发给商派矩阵中心，由矩阵中心代理请求淘宝/京东等平台 API。仓库内不含任何平台的签名算法与 SDK 实现（grep app_key/sign_method/secret 为 0 结果）。脱离商派服务，erpapi 一步都跑不通。

证据：app/base/defined.php:21 · app/erpapi/lib/caller.php:239 center_call() · 44 个文件引用 certi_id · 972 个文件含 matrix
事实 2必需 6 平台中，抖音适配完全缺失

matrix 目录逐一核对：淘宝 ✓(16 文件)、天猫 ✓(27)、京东 ✓ jd(7)+360buy(31)、拼多多 ✓(11)、小红书 ✓ xhs(8)+xiaohongshu(7)、唯品会 ✓ vop(8)——抖音 ✗（全仓库 grep douyin/抖音/抖店 = 0 个文件）。抖音是近年增量主力且报文/售后规则迭代最快，这个适配器无论如何都要从零写（估 1-1.5 人月）。

证据：app/erpapi/lib/shop/matrix/ 目录清单 · 全局 grep 0 结果
事实 3报文映射层与 ome 数据模型深度耦合，「只 fork 对接层」不成立

erpapi 1411 个文件中 381 个直接 app::get('ome') 调用订单/售后模型；matrix 映射层 645 个文件中 156 个内嵌 ome 表读写（如 taobao/request/aftersale.php 直接操作 return_product_taobao 模型）。这意味着路径 C（核心自研 + 对接层 fork）必须为 156 个文件重写模型访问适配层——复用价值大幅缩水。

证据：grep app::get('ome') 统计 · app/erpapi/lib/shop/matrix/taobao/request/aftersale.php 样例
事实 4框架是纯自研 ECOS，零主流生态，团队上手与维护全靠自力

composer.json 仅 4 个依赖（OSS SDK/Sentry/Monolog/guzzle-dev），MVC、队列、ORM(schema DSL)、事件(dbevent)、服务注册(services.xml) 全部自研。开源社区极小（87 star），遇到框架级 bug 无人可问。同时应公平指出：其工程质量不差——带 phpstan/phpunit/phpcs、Sentry 监控、Docker+supervisor 部署，且架构按远超日均 2 万单的规模设计，性能对我们的中规模场景绰绰有余。

证据：composer.json · app/base/lib/ 框架源码结构 · README 安装章节

4决策矩阵：什么情况选哪条

如果…选说明
上线时间是硬约束（<4 个月），且可接受商派矩阵服务年费与数据中转A速度唯一优先时的务实选择；但要立项时就把「矩阵中心替换」列入二期 roadmap，避免锁定固化
时间窗 6-9 个月可接受，追求长期自主可控（与既定自研决策一致）B（推荐）逆向文档已把商派 20 年业务沉淀转化为需求底稿，B 的「从零理解业务」成本已被前置消化
团队里有 ≥2 人深度熟悉商派/ECOS 代码（如过渡期运维团队）A 或 B 均可A 的上手成本假设被打破时可重新核算；但数据主权与锁定问题不因此消失
希望先快速验证业务模型再定终态过渡期方案直接用现有「ShopeX 对接通天晓」过渡方案跑业务，自研按 B 并行推进——不需要为验证而 fork
无论选哪条，两件事都躲不掉，请提前立项

① 自建平台 gateway（或采购商派矩阵服务）：签名、授权托管、限流、重试、报文日志——这是所有平台对接的地基，2-3 人月起；② 抖音适配器从零开发：开源商派没有，别处也抄不到现成的，1-1.5 人月，且需申请抖音开放平台资质（有审核周期，建议立即启动申请）。

5路径 B 落地要点（若采纳推荐）

  • 框架：Hyperf（Swoole 协程，与商派队列/Redis-Lua 机制心智最接近，高并发库存预占天然适配）或 Laravel（生态与招人最优）。中规模（≤2 万单/日）两者都撑得住，按团队熟悉度定，建议 1 周内做 spike 验证后拍板。
  • 域拆分：按逆向文档 00 的 9 大域收敛为 7 个服务边界（订单履约 / 库存 / 售后 / 采购经销 / 财务对账 / 平台 gateway / 组织权限+门户），首期单体分模块（modular monolith），不急于微服务。
  • 数据模型三大地基改造（相对商派）：① 库存记账 仓×SKU×货主 三元 + 借调规则；② 全业务单据携带货主维度（含财务）；③ 租户级行隔离（品牌方门户）。
  • 继承商派 7 大机制：审单插件链（位标记改结构化原因表）、合单指纹+缓冲窗、拆单策略注册表、预占独立流水+Redis Lua、api_log/api_fail 双表分级重试、售后三段式、元数据驱动 CRUD（schema DSL 思想用 Laravel Resource/Hyperf 注解实现）。
  • MVP 切分（4 条链路 × 4-6 人的现实排法）：M1（第 1-3 月）gateway+淘系/拼多多拉单 → 审单 → 推通天晓 → 发货回传 + 三元库存记账；M2（第 3-5 月）售后 + 京东/抖音/小红书/唯品会适配 + 库存同步全平台；M3（第 5-7 月）采购 + 金蝶对账 + 品牌方门户；M4（第 7-8 月）迁移双跑与切换。
