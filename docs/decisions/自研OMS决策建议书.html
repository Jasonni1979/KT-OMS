01背景与痛点

1.1 现状

公司作为电商代运营服务商，同时经营代运营（多品牌多店铺、平台授权经营、货权归品牌方）与经销（买断货权、采购入库、批发分销）两类业务。当前订单履约全链路依赖通天晓：OFS 订单履约系统 + WMS 仓储管理系统，覆盖淘宝/天猫、京东、拼多多、抖店、微信小店及私域渠道的订单处理，以及仓内 PDA、波次、复核、称重、发运作业。

1.2 为什么要动

痛点具体表现影响
技术运维受制于厂商问题响应依赖厂商排期，故障定位是黑盒，定制需求周期长、报价不可控大促保障被动，业务节奏被卡
厂商合作存在不确定性续约议价能力弱；OFS+WMS 双系统绑定同一厂商，依赖度过高商务与经营安全风险
知识产权不在自己手里订单中台作为业务最上游核心系统，代码与数据模型均不可控长期竞争力无法沉淀
双业务耦合支持不足代运营的货权分离、三方结算与经销的成本核算、批发价格体系，在通用 OFS 中难以两全财务对账靠人工，规模化受限

1.3 前序调研结论（2026-10-17，本建议书的依据）

  • MIT 协议的成熟 OMS/WMS 客观不存在；Apache-2.0 是事实标准，商业友好度不输 MIT（含专利授权与反诉终止条款），可闭源自研。
  • ShopeX ONEX OMS 是唯一「协议干净 + 业务完整 + 厂商级迭代」三重达标项：商派官方开源，Apache-2.0，v8.10.0 于 2026-09-26 发版；60+ 业务模块中 dealer（经销商）、taoguan*（淘宝官仓）、presale（预售）、vop（京东 VOP）、tgstockcost（库存成本）、purchase（采购）、finance（财务）、qimen（奇门对接）直接命中代运营与经销诉求，与通天晓 OFS 业务模型重合度最高。
  • 启航系（qihang）是功能陷阱：平台覆盖最广但协议为 AGPL-3.0，网络交互即触发全量开源义务，闭源商用硬性排除，只可作产品需求参考。
  • 「直接 fork 上生产」不成立：开源解决的是厂商绑架与知产归属，解决不了「谁来长期养这套代码」——必须自建团队接管。
  • 通天晓官方已声明 WMS 支持第三方 OMS 对接：标准 RESTful API 平台，预置出库订单、入库通知、退货预报、库存对账报文，先换 OMS 不动 WMS 的路径官方背书。

02建设目标与业务范围

2.1 建设目标

🎯 自主可控

订单中台源码在手，运维不再受厂商排期制约；对通天晓的依赖从 OFS+WMS 双依赖降为仅 WMS 单依赖，续约谈判地位显著改善。

🧩 双业务一套中台

代运营（货权分离、多品牌隔离、三方结算）与经销（买断货权、成本核算、批发体系）在同一订单中台上以货主/业务类型维度区分，不做两套系统。

⚡ 3 个月见效

MVP 聚焦代运营核心履约链路，单品牌试点上线；用最小变更拿到最大自主权，仓内作业零感知。

🔌 可插拔扩展

平台对接、WMS 对接、财务结算均按适配层设计，后续换 WMS、接新平台、整合财务数据源不动核心域模型。

2.2 业务范围界定

优先级范围说明
P0 · MVP代运营履约链路多平台订单归集、多品牌多店铺管理、平台授权、审单、寻源分仓、下发通天晓 WMS、物流回传、库存同步、基础结算对账
P1 · MVP 后 3-6 月经销业务链路采购管理、入库通知、成本核算、多仓调拨、批发价格体系、经销商（dealer）管理
P2 · 按需增值与深化预售、O2O/POS、京东 VOP、KPI 报表、财务系统深度整合（可插拔）、WMS 替换决策
不在范围仓内作业系统PDA、波次、复核、称重、发运、FEFO 全部保留在通天晓 WMS，本建议书不涉及
范围决策依据 代运营是收入基本盘、订单量与痛点最集中，且 ShopeX 底座对代运营模块（多店铺、货权、结算）覆盖最完整，故列 P0；经销链路依赖的 purchase / tgstockcost / dealer 模块底座中已有骨架，P1 阶段做适配增强而非从零建，投入可控。

03技术路线对比与推荐

3.1 三条候选路线

维度路线 A：ShopeX 底座二开
推荐		路线 B：纯从零自研路线 C：继续通天晓 OFS 优化
做法fork ShopeX ONEX OMS（Apache-2.0），自研团队接管源码，按双业务需求裁剪增强，逐步替换通天晓 OFS自建领域模型与代码框架，参考开源项目设计，不引入其代码不动系统，通过商务谈判改善 SLA 与响应
协议风险无。Apache-2.0 可闭源商用，保留 LICENSE/NOTICE 即可无（但需严格防火墙，防止团队参考 AGPL 项目代码造成污染）无
3 个月 MVP 可行性可行。60+ 模块已含多平台归集、审单、寻源、奇门对接，MVP 主要工作是裁剪、对接、验证不可行。仅平台 API 对接（淘宝/京东/拼多多/抖店/微信小店五套授权与订单模型）就需 3 个月以上不适用
投入（人力·年）约 3-5 人 × 0.5-1 年到稳定期约 6-10 人 × 1.5-2 年，且需要资深订单域架构师0 研发投入，持续支付厂商费用
自主可控高：源码在手，二开后与上游解耦自主演进最高：完全自有无改善
核心风险PHP/Swoole 技术栈团队适配成本；底座代码理解期；与上游版本分叉后的维护责任周期与人力远超预算；订单域坑位（超卖、拆合单、状态机）需全部自己踩厂商依赖与运维痛点原样保留，谈判地位不改善
痛点解决度OMS 侧全解，对通天晓依赖减半全解，但远水不解近渴不解决
推荐结论：路线 A（ShopeX 底座二开） 在「3-5 人小团队 + 3 个月 MVP」的约束下，路线 A 是唯一可行解。路线 B 的从零自研周期至少 18 个月、人力翻倍，不符合当前团队规模；路线 C 不解决任何根本痛点。「以 Apache-2.0 项目为骨架 + 自建核心领域模型 + 增量替换」正是前序调研认定的务实路径。
2026-10-23 补充修订：经源码级复核，底座准确定位为「多店铺数据模型 + 单运营主体运营视图」——多品牌数据钩子齐全（店铺挂组织/核算主体、订单带 org/cos 维度），但隔离强制层（行级权限/库存货主/品牌结算/品牌审单规则）需二开自建，+3-4 周进 M2。该修订不改变路线结论：隔离强制层在任何路线上都是必建增量，换底座只保留增量、丢掉重资产。详见《底座复核与多品牌隔离设计》。

3.2 路线 A 的三个关键工程决策

决策点选择理由
与上游的关系接管即分叉：fork 后建立内部主仓库，不再跟随上游自动合并；按季度评估上游安全补丁，人工挑选合入二开深度会迅速扩大 diff，自动合并成本高于收益；Apache-2.0 无回馈义务
技术栈保留 PHP / Swoole 主体，不做大重写；新增独立能力（如数据看板、对账 Job）可用团队熟悉的语言以独立服务 + API 方式挂接重写等于变相走路线 B；Swoole 队列性能足够支撑单品牌试点到全量
WMS 对接层优先复用底座 qimen（奇门）模块；若通天晓走私有 RESTful 报文，则新建独立适配器模块，核心域模型不感知 WMS 品牌可插拔设计，为 P2 阶段 WMS 替换决策保留选择权

4.3 与通天晓 WMS 的对接设计

  • 四类核心报文（通天晓官方预置标准）：出库订单下发、入库通知、退货预报、库存对账。MVP 阶段必须打通并做双向一致性校验。
  • 库存口径对齐责任转移：对接后 OMS 与 WMS 之间的库存一致性由自己团队保障，需建立日终自动对账 Job + 差异告警，这是过渡期最高优先级的稳定性工作。
  • 接口降级预案：WMS 接口异常时订单在 OMS 侧排队缓冲，恢复后自动补发，不丢单不重复下发（幂等键设计）。
