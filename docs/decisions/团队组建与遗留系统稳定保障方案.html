自研 OMS 配套执行方案 · 双轨制组织设计 + 通天晓知识抢救计划
版本 V1.02026-10-23配套文档：《自研 OMS 决策建议书》V1.0 状态：待批准执行
最紧急的一件事：知识抢救窗口只有 2-4 周，且不依赖立项审批 熟悉通天晓的经理已离职、可付费回访——这是当前唯一的高质量知识源，且记忆随时间衰减。 本周内启动 5 场专题回访（业务规则 / 结算口径 / 接口坑位 / 排障路径 / 事故复盘），2 名运维全程参加并当日产出纪要。 这件事的产出同时是自研 OMS 的需求输入（OFS 里沉淀的审单规则、结算口径就是新系统的业务需求），一次投入两处收益。 即使自研立项被否，这份知识资产也直接降低遗留系统的单点风险。
方案核心结论 ① 组织采用双轨制：遗留保障轨（2 运维 + 厂商 SLA，不动）与自研开发轨（新增 3.5-4 FTE）并行，技术负责人一人跨双轨做「桥」； ② 组建渠道为外招 + 内转混合：技术负责人与平台对接外招（带订单域/开放平台经验），后端与产品测试内转培养； ③ 2 名运维严禁抽调进开发——他们是遗留线最后的守线人，配置运维级能力按 3 个月路径升级到脚本/SQL 级； ④ 推荐编制：外招 2 + 内转 2（含 0.5 兼职）+ 2 运维不动，另设可选 PHP 顾问（4-6 周）与降级配置两档； ⑤ 冲突裁决原则：遗留稳定 > 开发进度；大促前后 1 个月为冻结窗口。

02双轨制组织设计

图 1 · 双轨制组织：技术负责人为桥，遗留轨守线、开发轨攻坚，2 运维不进入开发轨

2.1 为什么是双轨而不是「一套人马兼顾」

  • 技能不重叠：遗留线需要的是配置操作与厂商协调能力，开发线需要的是二开编码能力；让运维兼开发会两头失守。
  • 责任可追溯：切换期任何事故必须能立刻判定「遗留问题还是新系统问题」，双轨边界即责任边界。
  • 回退能力的前提：建议书承诺的全程可回退，依赖遗留线在整个切换期保持可运行状态——这要求遗留线有独立且不被稀释的守线力量。

2.2 技术负责人的「桥」职责（本方案最关键的一个岗位）

职责内容
遗留知识所有者主持 5 场离职经理回访，成为公司内部唯一「既懂 OFS 业务规则、又懂新系统架构」的人；知识手册的最终审校人
架构与二开决策底座裁剪清单、领域模型把关、WMS 适配器方案（见建议书第 4 章）
值班与终判遗留线 P1 故障的第二响应人（第一响应为运维）；判定故障归属轨并路由
时间分配M1：遗留 40% / 开发 60%；M2 起：遗留 20% / 开发 80%；全量切换后遗留归零

3.2 内转人员的筛选与培养

  • 筛选三问：愿不愿意接一个要养 3 年以上的系统？能不能接受前 3 个月读存量代码的枯燥？原部门放人的时间窗是什么？（第三问需发起人层面协调，避免「名义转岗、实际兼着原活」）
  • 培养路径：W4-W6 PHP/Swoole 培训（顾问或技术负责人带）→ W6 起认领一个独立小模块（如监控告警 Job）→ M2 进入核心二开（审单/库存）。
  • 防单点：每个核心模块（审单/库存/对接/对账）必须有 2 人读过代码，每周代码走读会制度化，文档与领域模型图沉淀在仓库内。

3.3 外招的两个实操建议

  • 技术负责人面试加一场「读码题」：给一段 ShopeX 底座的真实订单状态机代码，让候选人 45 分钟内讲清逻辑并指出两个潜在坑——比八股文面试更能预测上手速度。
  • offer 里写明项目性质：「接管开源底座做企业自研、非外包交付、系统生命周期 3 年以上」——这类项目对订单域老兵有吸引力，写清楚能降低入职后落差流失。

04通天晓知识抢救计划（紧急 · 2-4 周窗口）

4.1 五场专题回访（每场 2-3 小时，2 运维 + 技术负责人参加）

#专题必须挖出的内容产出物
1业务规则全量OFS 中全部审单规则、拆合单逻辑、寻源/分仓规则、异常单处理惯例；哪些是「配置出来的」、哪些是「厂商改代码改出来的」《OFS 业务规则清单》——自研 OMS 审单域的需求底稿
2结算与对账口径代运营三方结算的账单来源、对账维度、差异处理惯例；经销成本口径；哪些环节靠人工 Excel 兜底《结算口径说明书》——结算域 P0 需求 + 财务可插拔层输入
3接口与集成坑位通天晓 WMS 四类报文的实际字段与文档差异、历史联调踩过的坑、各平台 API 的限流/幂等怪癖、私域订单的特殊链路《接口坑位手册》——M2 WMS 联调的避雷图
4排障路径与权限常见故障的排查顺序（看哪张表、哪个日志、哪个配置项）；OFS/WMS 全部账号权限清单与申请路径；厂商工单的正确提法（怎么提才快）《排障 Runbook》+ 权限矩阵——2 运维日常作战手册
5事故复盘近 2 年 P1/P2 事故逐条过：根因、止血动作、是否复发；大促保障的固定动作清单《事故案例库》——监控告警项设计的直接依据

4.2 执行规则

  • 当日纪要：每场回访结束当天，由产品/测试（兼职）整理结构化纪要入仓库，经理本人确认签字（邮件确认即可）——避免二手信息失真。
  • 付费方式：按场次结算顾问费，5 场打包谈；明确保密与不竞争条款，降低对方顾虑。
  • 挖「为什么」不挖「是什么」：配置项截图运维自己就能截，经理的价值在于解释「这条规则为什么存在、改它会引发什么」——访谈提纲全部围绕 why 设计。
  • 录屏留档：经同意后全程录屏，作为纪要的原始凭证，后续新人入职培训直接用。
一次投入，两处收益 五场回访的产出物 1、2 直接是建议书第 5 章 P0 功能清单的需求细化输入（审单规则、结算口径）；产出物 3、4、5 直接是第 5 章遗留保障体系的作战手册。 这也是为什么即使自研立项暂缓，本计划也应独立执行。

5.3 厂商 SLA 重确认清单（本周发函）

【2026-10-23 断供修订】与通天晓发生技术纠纷、合同已到期/临期，厂商支持不可依赖。本清单降级为商务轨道的谈判议题清单（由发起人掌握节奏），技术侧防御改按《厂商断供应急预案》执行：72 小时紧急行动（账号/许可核实、数据备份抢救、接口资产抢救、证据保全）、WMS 黑盒自救体系、接口逆向工程替代厂商联调。

  • 响应时效分级：P1（停单）/ P2（功能异常）/ P3（咨询）的响应与解决时限书面确认；
  • 代码级问题的支持边界：内部专家离职后，厂商是否仍承担代码级排障？是否额外收费？
  • WMS 接口联调配合：对接排期、测试环境、报文清单（与建议书第 8 章风险项联动，同一封函件提出，减少商务往返）；
  • 续约条款预沟通：OFS 合同到期时间与退出条款（为切换窗口与热备成本测算提供输入）。

06双轨协同与冲突裁决规则

机制规则
每周双轨同步会30 分钟固定议程：遗留线风险通报 → 开发线进度与口径问题 → 值班交接。纪要入仓库，缺席者必读
冲突裁决原则：遗留稳定 > 开发进度。技术负责人可裁决日常冲突；涉及人力抽调或冻结窗口调整的，上报发起人终裁
人力防火墙2 名运维不进入开发轨排期；开发轨成员不承接遗留线日常工单（P1 事故支援除外，且事后补时）
知识单向流动遗留线产出的 Runbook/事故库/口径文档，开发轨必须消费（作为需求与告警设计输入）；开发轨产出的监控工具反哺遗留线——双轨唯一允许的「资源流动」是文档与工具，不是人
切换期特别规则灰度切流期间遗留线进入「热备值守」状态：运维每日核对回切预案可用性；任何品牌回切演练每季度 1 次
