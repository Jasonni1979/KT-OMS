底座复核与多品牌隔离设计

对「ShopeX ONEX OMS 是单品牌系统」质疑的代码级复核 · 混合隔离模型设计
版本 V1.02026-10-23 复核方式：GitHub 源码实测（v8.10.x，167MB 全量克隆） 修订对象：《自研 OMS 决策建议书》V1.0
复核结论（一句话） 团队的观察对了一半：ShopeX 底座的数据模型不是单品牌（店铺挂组织/核算主体、订单带 org/cos 维度、品牌主表与货主概念都在）， 但隔离的强制层没有落地（无行级数据权限、库存无货主维度、结算不按品牌闭环、审单规则无组织维度）—— 准确表述是「多店铺数据模型 + 单运营主体运营视图」。 缺口在强制层而非领域模型，属于「在已有钩子上加执行层」的二开工作（预估 +3-4 周进 M2），不构成换底座的理由； 隔离模型按已确认决策采用混合制：逻辑隔离为主 + 敏感品牌物理隔离。
为什么换底座解决不了这个问题 「按店铺隔离独立管理」是业务需求，不是底座特性。无论选 ShopeX、启航（AGPL 已排除）还是从零自研， 行级数据权限、库存货主维度、品牌结算闭环、品牌级审单规则这四件事都必须自建。 底座的价值在平台对接、订单域、库存五态这些「重资产」；隔离强制层是增量，增量在哪条路线上都逃不掉。 换底座只会把增量保留、同时丢掉重资产。

01代码实测证据

复核方式：全量克隆 ShopeX/OMS 仓库（Apache-2.0，v8.10.x，167MB），对 app/ 下 60+ 模块的 dbschema（表结构定义）与 lib（业务逻辑）做定向检索。以下为关键证据。

1.1 数据模型层：多品牌钩子齐全（修正「单品牌」判断）

证据代码位置含义
店铺表带组织归属ome/shop：字段 org_id、cos_id、ind_cos_id、node_id/node_type店铺可挂到组织节点与核算主体下，多品牌归属的数据钩子存在
组织树 + 核算中心树organization 模块：org 表（org_type/org_level_num/parent_id 层级树）+ cos 表（初始数据=总部 HQ / 经销公司 DC）多经营主体模型存在，且区分「组织」与「核算中心」两套树
订单表带组织维度ome/orders：字段 shop_id、org_id、cos_id；索引 idx_orgid_ordertype...、ind_cos_id、idx_shopid_orderid_createtime订单可按组织/核算中心检索与统计，索引已建好
品牌主数据ome/brand（brand_code/name/keywords）、ome/goods.brand_id、ome/type_brand品牌作为主数据实体存在
货主概念局部存在console/wms_transferorder.owner_code、inventorydepth/shop_skus.cos_id调拨单与店铺库存设置已有货主/核算维度字段

1.2 强制层：隔离未落地（团队判断成立的部分 = 真缺口）

缺口实测证据后果
无行级数据权限pam/account 仅账户字段；pam/auth = account_id + module + module_uid + 序列化 data blob（模块级功能权限）；全库无 shop/org 范围权限字段，lib 层无强制过滤逻辑账号登录后理论上可见全部店铺订单；「按店铺隔离独立管理」在权限层是空的
库存无货主维度console 核心库存表无 org/cos/owner 字段（仅调拨单有 owner_code）；库存只挂 shop_id库存五态按店铺挂、不按品牌/货主挂；货权隔离只能靠「店铺集合=品牌」的口头约定
结算不按品牌闭环finance/billcenter 的 lib 中无 cos_id 使用；cos 重度使用集中在 dealer（35 个文件，经销线）代运营三方结算按品牌/核算主体出账需自建
审单规则无组织维度omeauto lib 中无 org/cos 过滤逻辑审单规则全局生效，无法按品牌配置差异规则
无多租户产品承诺docs / README / CHANGELOG 无多品牌、多货主、tenant 相关描述厂商产品定位确为「多店铺、单运营主体」——团队印象的来源，方向正确

02修订后的底座评价

评价维度10-17 调研原结论10-23 复核修订
协议与合规Apache-2.0，三重达标唯一项维持，不受影响
业务完整度「业务完整度最高，与 OFS 重合度最高」修订为：履约链路完整度高；多品牌运营视图缺失。60+ 模块的价值在订单/库存/对接/经销，不在隔离
多品牌适配未单独评估（隐含假设底座可直接承载）新增结论：数据模型可承载、强制层需自建；四组件二开 +3-4 周进 M2
路线结论路线 A（底座二开）推荐维持路线 A，理由见开篇：隔离强制层在任何路线上都是必建增量，底座重资产价值不变
给团队的回应口径 「商派开源 OMS 不满足多品牌需求」这个说法，精确版本是：「商派开源 OMS 开箱不满足多品牌隔离的强制要求，但其数据模型预留了全部钩子，强制层二开可控」。 两者差别决定了是「换底座」还是「加二开」——实测支持后者。

03混合隔离模型总体设计

图 1 · 混合隔离模型：逻辑主实例承载绝大多数品牌（强制层四组件保证隔离），敏感品牌独立实例，统一门户与看板只做只读聚合

3.1 品牌入驻路由规则（进逻辑实例还是开物理实例）

判定条件（满足任一即物理隔离）说明
合同条款明确要求独立系统/独立数据库法务在品牌签约评审时勾选，作为路由依据存档
品牌方审计要求数据物理隔离（如上市公司内控、外资合规）以品牌方书面审计要求为准
品牌方禁止其数据与其他品牌同库存储数据主权条款触发
默认：以上均不满足进逻辑隔离主实例，享受共享运维与跨品牌聚合能力

路由决策人：发起人（商务条款）+ 技术负责人（可行性）双签；决策记录入品牌档案。迁移通道：逻辑实例品牌后续触发物理条件时，按「新品牌接入 SOP」导出该品牌全量数据开新实例（数据导出工具在 S0 与迁移工具链一并建设，复用 B3 的 ETL 组件反向使用）。

04逻辑隔离强制层（四组件，M2 交付）

组件设计验收标准
① 行级数据权限中间件账号→角色→店铺集合（品牌）三级授权模型，替代 pam 模块级权限；在列表/详情/导出/接口四层统一注入过滤条件（中间件拦截，禁止业务代码各自拼条件）；越权访问记审计日志并告警渗透测试：A 品牌账号对 B 品牌订单的列表/详情/导出/API 四类访问全部 403；审计日志留痕
② 库存货主维度库存表增加货主字段（复用 cos_id 语义并显式命名为 owner），五态库存按「货主+仓+SKU」存储；店铺-货主映射表为唯一权威；平台可售库存按货主归集计算同 SKU 两货主库存互不可见、互不占用；超卖压测中货主间零串货
③ 品牌结算闭环结算单/对账单强制带 cos_id；佣金与费用归集按品牌维度出账；品牌间费用分摊规则配置化；与财务可插拔适配层对接同一结算周期可按品牌独立出对账单，合计与总账勾稽一致
④ 品牌级审单规则审单规则引擎加组织维度：规则作用域=全局/品牌/店铺三级，品牌规则优先于全局规则；规则变更留痕两品牌配置冲突规则（如赠品策略不同）互不影响，回归测试通过
四组件的实现顺序与依赖 ②库存货主维度先行（数据模型变更，影响面最大，需最先定稿并做历史库存回填）→ ①权限中间件（依赖店铺-货主映射表）→ ④审单规则（依赖组织维度字段）→ ③结算闭环（依赖前三者的口径稳定）。 顺序错误的代价：库存模型后改会导致已迁移数据二次回填。

05敏感品牌物理隔离

  • 实例形态：独立数据库 + 独立应用部署（底座原生单品牌跑法，零隔离二开成本）；共享代码仓库与发布流水线，配置化区分实例参数。
  • 运维成本控法：实例标准化（同一镜像、同一配置模板、同一监控模板），新增物理实例的边际运维成本控制在 0.2 人月/实例以内；物理实例数量设上限预警（>3 个时复盘是否该回到逻辑隔离+合规增强）。
  • 数据边界：业务数据不出实例；仅脱敏聚合指标（单量/GMV/履约时效）上送统一看板；跨实例报表在聚合层完成，不回传明细。
  • 升级策略：代码同源，升级包统一发布；物理实例可错峰升级（先逻辑主实例验证 1 周再推物理实例）——这反而是物理隔离的附带收益：多了一个生产验证环境。

06对里程碑与投入的影响

M1 新增动作底座研读 + 裁剪清单裁剪清单中新增「隔离钩子盘点」：org/cos 字段使用面、pam 替换影响面评估
门禁 G1 新增项双跑一致率≥99.9%追加：隔离渗透测试通过（四组件验收标准全绿）才允许进入 S2 试点切换
人力3.5-4 FTEM2 高峰期后端 +0.5（内转第二名后端提前进场），总编制不变、峰值错开
MVP 周期3 个月维持 3 个月：四组件与 WMS 联调并行；若渗透测试不达标则顺延 S2，不顺延不豁免
试点品牌选择订单量中等、SKU 不复杂追加条件：试点品牌必须进逻辑实例（验证强制层），敏感品牌排后切换

07风险与验收

风险等级应对兜底
中间件注入过滤有遗漏点（某接口绕过权限）高接口清单全量盘点+自动化越权扫描（CI 内置）；导出与 API 与页面同权渗透测试不达标=门禁不达标，不切换
库存货主维度回填历史数据出错高回填按店铺-货主映射表批量执行+逐仓对账；回填前后库存合计校验回填失败回滚快照，映射表修正后重跑
物理实例运维成本超预期中实例标准化模板；>3 个实例触发架构复盘新签品牌默认逻辑隔离+合同谈判规避物理条款
品牌路由判定争议（商务想全物理/技术想全逻辑）中路由规则写成判定表（3.1），双签留痕；个案争议上发起人—（制度保障）
跨品牌聚合看板泄露明细中聚合层只读+脱敏字段白名单；看板权限独立于业务权限看板下线不影响履约
收尾结论 底座选型维持路线 A 不变；「多品牌隔离」从隐含假设升级为显式 P0 二开项（强制层四组件 + 混合隔离模型）， 进入 M2 范围并挂门禁 G1。建议据此修订《自研 OMS 决策建议书》第 3、5 章表述，其余章节不受影响。 本报告源码证据可复核：克隆仓库后按第 1 章代码位置逐条查验。
