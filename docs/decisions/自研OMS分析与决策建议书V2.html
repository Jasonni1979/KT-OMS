0核心结论（只读这一段也够）

① 路线修正：从「Fork 商派二次开发」改为「PHP 新架构自研，商派降级为参考实现」

代码取证发现：开源商派的平台对接层无法独立使用——所有平台 API 硬编码经「商派矩阵中心」（matrix-gw-open.shopex.cn）代理并需 license 证书认证，仓库内不含任何平台签名/SDK 实现；且不含抖音适配（必需 6 平台之一，0 个文件）。Fork 的最大卖点「平台对接现成」不成立，其残余价值（业务模型理解）已通过 8 份逆向文档提前兑现。

② 逆向工程的价值已经落袋：不用商派的代码，但继承它的业务模型与 7 大机制

711 张表、9,849 个字段、四大业务域流程全部文档化（约 43 万字节、29 张图）。审单插件链、合单指纹、拆单策略注册表、Redis+Lua 库存预占、api_fail 分级重试、售后三段式、元数据驱动 CRUD——商派 20 年电商 ERP 沉淀的机制精华全部转化为自研的需求底稿，「从零理解业务」的成本已被前置消化。

③ 自研必须做三大模型改造，这是商派模型撑不住我们业务的地方

三元库存记账（仓×SKU×货主，支持隔离+借调）、货主维度贯穿全域单据（含财务——商派财务单据无货主维度，是其最大缺口）、租户级行隔离（品牌方多租户门户 + SaaS 化预留）。在 113 万行存量代码上做这三处地基改造，风险高于按新模型重新设计。

④ 投入与节奏：4-6 人 × 7-8 个月，M0-M4 五阶段，按品牌灰度切换

M0 技术验证（2-4 周）→ M1 正向履约+库存（1-3 月）→ M2 售后+6 平台+多 WMS（3-5 月）→ M3 采购+金蝶对账+品牌方门户（5-7 月）→ M4 近 3 年订单迁移+灰度切换（7-8 月）。全程保留通天晓 OFS 回退能力。比 Fork 路线多 2-3 个月，换取数据主权、零供应商锁定与干净的长期架构。

⑤ 本周必须启动的两件事

抖音开放平台资质申请（审核周期长，适配器要从零写）；框架 spike（Hyperf vs Laravel，1 周定型）。另有金蝶版本确认、WMS 接口文档收集、业务量级数据补齐四项并行推进。

1背景与痛点

1.1 现状

公司作为电商代运营服务商，同时经营代运营（多品牌多店铺、平台授权经营、货权归品牌方、收服务费/佣金）与经销（凯淳买断货权、采购入库、成本核算）两类业务。当前订单履约全链路依赖通天晓 OFS + WMS 双系统，覆盖淘宝/天猫、京东、拼多多、抖音、小红书、唯品会及私域渠道。

2.2 代码取证：4 个改变路线判断的决定性事实

事实 1 · 开源版的平台对接是「半截子」：签名与传输在商派的 SaaS 网关里

erpapi 的 76 个平台目录（645 个映射文件）只做「OMS 字段 ↔ 平台报文」翻译；真正的 HTTP 出口硬编码 MATRIX_URL = 'https://matrix-gw-open.shopex.cn/'，每次调用携带 certi_id（商派 license 证书）签名后发给商派矩阵中心，由其代理请求平台 API。仓库内不含任何平台签名算法与 SDK 实现。脱离商派商业服务，erpapi 一步都跑不通；要继续用则需按年采购矩阵服务，且消费者订单数据经商派服务器中转——与 PIPL 合规诉求和品牌方信任直接冲突。
证据：app/base/defined.php:21 · app/erpapi/lib/caller.php:239 center_call() · 44 文件引用 certi_id · 972 文件含 matrix

事实 2 · 必需 6 平台中，抖音适配完全缺失

逐一核对 matrix 目录：淘宝 ✓(16 文件)、天猫 ✓(27)、京东 ✓(7+31)、拼多多 ✓(11)、小红书 ✓(8+7)、唯品会 ✓(8)——抖音 ✗（全仓库 grep douyin/抖音/抖店 = 0 文件）。抖音是近年增量主力且报文规则迭代最快，该适配器无论如何要从零写（1-1.5 人月），资质申请还有审核周期。
证据：app/erpapi/lib/shop/matrix/ 目录清单 · 全局 grep 0 结果

事实 3 · 对接层与订单大内核深度耦合，「只 fork 对接层」不成立

erpapi 1,411 个文件中 381 个直接调用 ome 订单/售后模型；matrix 映射层 645 个文件中 156 个内嵌 ome 表读写。混合路径（核心自研 + 对接层 fork）需为 156 个文件重写模型访问层，复用价值被改造成本吃掉。
证据：grep app::get('ome') 统计 · matrix/taobao/request/aftersale.php 样例

事实 4 · 框架是零生态自研 ECOS，但工程质量不差

composer 仅 4 个依赖，MVC/队列/ORM/事件/服务注册全自研，开源社区 87 star——框架级问题无人可问，新人只能读源码上手。公平地说：带 phpstan/phpunit/Sentry/Docker，架构按远超我们规模的量级设计，性能对中规模场景绰绰有余。问题不在质量，在生态与可维护性。

2.3 业务模型层面的关键发现（逆向文档沉淀，自研直接继承）

🧠

订单域

三套状态机并行；审单=23 插件位责任链+位标记；拆单 16 策略注册表（拆单产物是发货单而非新订单）；合单指纹预计算+缓冲时间窗；复审快照+库存冻结。

📦

库存域

三层主体（销售物料→基础物料→仓×SKU）；五口径库存；预占走独立流水表+Redis Lua 原子扣减（不落主字段）——高并发关键设计；移动加权成本。

💰

采购财务域

采购单 5 状态分离；现购按单挂账/赊购按入库挂账；供应商台账（期初/增加/已付/期末）；核销三档+差异科目映射；运费预估/实际双账单对账。

🔌

对接与售后域

拉单三保险（消息推送+定时增量+单拉补偿）；api_log/api_fail 双表分级重试；售后三段式（申请单/执行单/退款单）；换货=退货+0元新单复用正向履约。

商派模型的 4 个明确缺陷（自研必须规避）

① ome 大内核（196 表/1,127 文件混装订单商品会员库存售后）；② erpapi 强依赖矩阵中心；③ 每平台一张售后镜像表（15 张 return_product_*）；④ 财务单据不带货主维度——多品牌代运营无法分账，是最大业务缺口。

5推荐决策与理由

推荐（已拍板）：方案 B —— PHP 新架构自研

框架：Hyperf 3（Swoole 协程）优先，Laravel 11 备选，M0 一周 spike 压测定型。架构风格：模块化单体（7 域严格边界），大促瓶颈出现时库存域/gateway 域优先拆出。商派代码定位：参考实现——继承业务模型与 7 大机制，不 fork、不复制代码（Apache-2.0 合规无虞）。

五条核心理由

  • 理由 1 · Fork 的经济性前提已崩塌：平台对接层（最大可复用资产）取证证明不可独立使用，A 方案实际只省 2-3 个月，却要背锁定与数据主权风险。
  • 理由 2 · 我们的三大核心需求恰好是商派模型的地基缺陷：货主隔离库存、货主维度财务、多租户门户——在存量代码上打地基补丁，比按新地基盖楼更贵更险。
  • 理由 3 · 逆向文档已兑现「不从零理解业务」：711 表全解析 + 四域流程 + 7 大机制文档化，B 方案最大的传统劣势（业务理解成本）已被前置消化。
  • 理由 4 · 与既定战略一致：自主可控、知产在手、K-AIDE 协同、SaaS 化预留——都要求干净的自有架构而非改造别人的旧楼。
  • 理由 5 · 团队可持续性：Hyperf/Laravel 人才市场充足，ECOS 只有商派自己会——「谁来长期养这套代码」的答案必须是「市场上招得到的人」。

例外条款（何时应重新考虑 A）

仅当管理层设定 <4 个月的硬性上线死线且接受矩阵中心年费与数据中转时，A 才值得重启评估；即便选 A，也须立项时将「矩阵中心替换」列入二期 roadmap，避免锁定固化。

7实施计划与投入

7.1 里程碑（详见《08-MVP实施计划》）

M0

技术验证与地基（2-4 周）

框架 spike 定型 · gateway 打通淘宝真实拉单 · 三元库存 Redis Lua 预占原型压测 · K8s/CI/CD · 7 域核心表 DDL V1 · 抖音资质申请提交。出口：最大不确定性全部消除。

M1

正向履约 + 库存（第 1-3 月，心脏）

拉单→审单（插件链+人工工作台）→拆合单→分仓→推通天晓→发货回传；三元库存记账/预占/借调/五口径/成本；按店铺可配置库存同步；淘系+拼多多适配器。出口：一个真实品牌全自动跑通全链路，库存账实一致，大促级压测通过。

M2

售后 + 全平台 + 多 WMS（第 3-5 月）

售后三段式全自动化；京东/抖音/小红书/唯品会适配器补全；多 WMS 路由；三类电子面单；团购/福袋/异常单/复审。出口：6 平台全打通，售后自动跑通。

M3

采购 + 财务对账 + 门户（第 5-7 月）

采购全链路（审批推泛微 OA）；对账/核销/运费/发票 + 金蝶集成层 + 排查工具；品牌方多租户门户；权限/审计/审批中心；固定报表。出口：品牌方登录只看自己数据，财务单据可供给金蝶。

M4

迁移双跑 + 灰度切换（第 7-8 月）

近 3 年订单异构迁移+清洗；期初库存对齐（含货主维度）；按品牌分批灰度（切换单元内店铺全旧或全新，避免库存双扣）；双跑对账；大促演练。出口：首品牌切换稳定，具备推全量能力。

8风险与回退

风险等级应对
抖音适配从零 + 资质审核周期高本周提交资质申请；M2 优先排期；期间抖音单量走过渡方案兜底

近 3 年订单迁移量级（最高 2,200 万单）高迁移工具 M1 并行设计；分批迁移；先期初+在途后历史；对账脚本验收
金蝶接口形态未知中财务部门尽快确认版本；集成层可插拔设计不绑定
多 WMS 路由抽象不当中尽早收集通天晓+第二家 WMS 接口文档，以此定抽象
灰度切换期库存双扣中切换单元=品牌（单元内店铺全旧或全新）；期初对齐脚本为切换前置门禁
Hyperf 团队熟悉度不足中M0 一周 spike；不达标退 Laravel（生态更稳）
4-6 人做 4 链路范围偏大中M1→M2→M3 串行推进；若人力到位延迟，先砍 M3 门户自动化程度（人工兜底）保 M1/M2
回退方案（全程保留）

灰度并行期内通天晓 OFS 随时可回切：切换以品牌为单位，未切换品牌继续在 OFS 运行；已切换品牌出现严重问题时，凭期初对齐脚本与双跑对账数据可回退到 OFS，WMS 仓内作业全程零感知（OMS 侧回退不影响仓内）。M4 完成全量切换并稳定一个完整大促周期后，方可下线 OFS。
