# KT-OMS 架构改造设计：契约化模块化单体

**版本** V1 草案（待评审） · **日期** 2026-10-26 · **状态** 待 Jason 确认后进入 P0

---

## 一、决策摘要

| 项 | 决策 | 依据 |
|---|---|---|
| 架构路线 | **契约化模块化单体**（不拆进程） | 关键域强一致 + 无生产部署 + 目标是 AI 可独立开发 |
| 模块数 | **8 个业务模块** + 1 个仿真工具域 | 切分准则：单 agent 上下文可完整装下 |
| 切分准则 | 单 service ≤ 500 行 / 单模块 ≤ 12 文件 / 单表唯一写者 | 「让 AI agent 逐个开发」的硬约束 |
| 跨模块通信 | **只读接口优先**（不引入消息队列） | 你的选择；关键域必须强一致 |
| 跨模块写的处理 | 允许调用对方**公开写接口**，但须在 contract.md 登记 | 避免为拆包引入 Saga 复杂度 |
| 门禁强度 | **先 warn 观察 2 周 → 再 fail** | 你的选择；防误伤正常开发 |
| 落地顺序 | P0 契约中心 → P1 目录重组 → P2 跨模块收口 → P3 巨型 service 拆分 | 低风险优先 |
| 为将来拆进程 | 契约不变 → 目录换独立包 + HTTP/MQ 适配，**业务代码零改动** | 规划扩多团队 |

## 二、约束 → 方案映射

| 你的回答 | 排除了什么 | 决定了什么 |
|---|---|---|
| 「AI agent 逐个开发，避免底层错误」 | 排除「只加文档不改结构」 | 必须有**物理目录边界** + **机器可读的归属声明** |
| 「关键域必须强一致」 | 排除「拆进程 + Saga 最终一致」 | 跨模块**写**仍走同步调用 + 本地事务 |
| 「还没生产部署」 | 排除「现在拆进程」（纯返工） | 先做零风险的结构改造 |
| 「规划扩多团队」 | 排除「永远不拆」 | 契约是未来拆服务的**免费副产品** |
| 「只读接口优先」 | 排除「现在引入 MQ」 | 跨模块读走公开接口；写走公开写接口 + 登记 |
| 「先 warn 后 fail」 | 排除「一次性上硬门禁」 | 门禁分两阶段上线 |

## 三、现状事实（实测，非估计）

| 维度 | 实测值 |
|---|---|
| 后端 service | **39 个 / 19,443 行** |
| API 端点 | **195 个**（17 个 api 模块） |
| 前端 | 26 个 Vue 页 / 5,309 行 |
| 数据库 | **单 MySQL 实例**，12 个 schema，373 张表（已建模 76） |
| 跨域调用 | 全部**进程内直接 import**（无网络边界） |
| 事务 | 12+ 个 service 各自 `commit`，无 Unit of Work |
| 超 900 行的 service | 6 个（最大 `delivery_service` 1403 行） |

### 3.1 表所有权现状（重要）

45 张表被写入。其中 **20+ 张由 `scenario` 一个 service 写**（`ord_order` / `inv_material` / `inv_stock_ledger` / `ord_receiver` / `org_owner` …）。

> `scenario` 是**仿真造数工具**，不是业务写者。它却住在 `app/services/` 里、与业务 service 平级，且依赖 9 个 service。
> **处置**：剥离到 `app/tools/simulation/`，明确标注「非业务写者」，并加门禁禁止业务 service 引用它。

真正跨 service 写的表只有 1 张：`oms_base.bas_event_outbox`（本来就是 outbox 表，多写者合理）→ **数据边界天然清晰，切分成本低**。

### 3.2 跨模块调用现状（决定改造规模）

**18 条跨模块边，仅 2 对双向**：

| 双向对 | 具体调用 | 性质 |
|---|---|---|
| **M4 ↔ M7** | `delivery_service→wms_channel`（推指令/叫回）＋ `wms_events→delivery_service`（回传编排） | 请求-回调对，非逻辑环 |
| **M5 ↔ M6** | `abnormal_action→aftersale`（转售后）＋ `modify→abnormal`（改单联动） | 业务协作，非逻辑环 |

> 这两处**不是架构腐化**，是业务上真实的双向协作。契约上登记为「回调关系 / 业务协作」，不视为违规。
> 真正需要禁止的是**底层模块依赖高层模块** —— 当前 **0 处违规**（M1 无出边、M2 只依赖 M1）。这是好消息：模块化改造不需要"解环"，只需要**建边界 + 显式登记**。

### 3.3 模块内循环

`wms_channel ⇄ wms_events`（同属 M7）→ P3 拆分时必须消除。

### 5.3 门禁规则（4 条，可机器判定）

| 规则 | 判定 | 当前违规 |
|---|---|---|
| **R1 底层不依赖高层** | M1/M2 不得 import M3+ | **0** ✓ |
| **R2 跨模块只走 contract** | 跨模块 import 的符号必须来自对方的 `contract.py` | **0** ✓（P2 收口，105 → 0，已转 fail） |
| **R3 表所有权唯一** | 一张表的写者集合 = 1（`bas_event_outbox` 白名单除外） | **0** ✓ |
| **R4 上下文体积** | 单 service ≤ 500 行；单模块 ≤ 20 文件且总行数 ≤ 6000 | **0** ✓（P3 拆分，11 → 0，已转 fail） |

> **R2 是本次改造的核心机制**：每个模块只有 `contract.py` 一个公开面，其余全是内部实现。跨模块只能 import `contract.py` 里的符号。AI agent 拿到一个模块时，只需读 `contract.py` 就知道能对外做什么。

> **R4 为什么这么定**：项目的目标是「让 AI agent 逐个开发、不互相踩」。
> agent 改一个 1400 行的 service 要把 1400 行全读进上下文 —— 越大越容易改错、越容易漏边界条件。
> 拆分的直接收益是让 agent 每次只读 300 行。真正约束上下文的是**单文件行数**与**模块总行数**，
> 「文件数」只是「导航不至于失控」的粗略护栏（拆分本身必然增加文件数，故由 12 放宽到 20）。

## 六、契约中心（P0 的核心交付）

### 6.1 为什么这是「底层错误」的头号根因

现状：枚举与状态机常量**散落在 39 个 service 里各抄一份**。DDL 的 COMMENT 才是权威，但代码里的常量是手抄的 → 必然漂移。

W9 已实测两处漂移：
- `aftersale.py` 换货类型缺「待审核 → 换货执行中」边 → 换货审核必然报「不可流转」
- `abnormal_ext.py` 批次阶段表缺边 → 阶段推进失败

**这类 bug 每次都要靠人眼发现，且发现时已晚一个批次。**

### 6.2 设计

`app/contracts/` 作为**唯一事实源**：

| 文件 | 内容 | 生成方式 |
|---|---|---|
| `enums.py` | 所有状态/类型枚举（含中文标签） | **从 DDL COMMENT 自动生成** |
| `transitions.py` | 全部状态机流转表 | **从 SRS 流转表自动生成** |
| `errors.py` | 错误分级（通道侧 `err_class` / 平台侧 `err_level` 两套，**不混用**） | 手写 + 门禁校验 |
| `ids.py` | 单号规则（RA/MA/RF/DLV/BN 前缀） | 手写 + 门禁校验 |

**自动生成是关键的**：DDL 已是权威源（`tools/check_model_ddl.py` 已证明可从 information_schema 读取），所以枚举不必手抄 —— 从 DDL COMMENT 生成，**漂移在物理上不可能发生**。

### 6.3 门禁

`tools/check_contract_ddl.py`：比对「代码里的枚举值集合」↔「DDL COMMENT 里的枚举值集合」，不一致直接失败。
→ 这条门禁会**一次性把现存的所有枚举漂移全部暴露出来**，逐个修完即根治。

## 八、跨模块只读接口契约

### 8.1 各模块对外只读接口（首批）

| 模块 | 只读接口 | 替代的现有直接调用 |
|---|---|---|
| **M1** | `master.get_node/list_nodes/children`、`branch_owner.list_by_owner`、`permission.get_scope` | `material→master` |
| **M2** | `stock_ledger.available_of/get_balance/query`、`sku_mapping.find_sales_material`、`sellable.calc`、`material.get/list_all`、`freeze.query_logs` | `audit_plugins→stock_ledger`、`order_create→sku_mapping` |
| **M3** | `audit_engine.blocked/reason_codes`、`audit_rule.matches/explain` | `abnormal_action→audit_engine` |
| **M4** | `delivery_service.get`、`dispatch_service.get_fulfill_view`、`plan_executor.list_plans`、`split_service.get` | `abnormal_action/stockout_strategy→plan_executor/dispatch_service` |
| **M5** | `abnormal.types_all/reason_dict/get`、`abnormal_ext.batch_sla_status/list_pause_logs` | `audit_engine→abnormal`、`modify→abnormal` |
| **M6** | `aftersale.list_applies/get_apply`、`modify.list_modifies/get_modify` | `abnormal_action→aftersale` |
| **M7** | `gateway.call`、`pull.get_watermark`、`sync.sync_status`、`wms_channel.query_order`、`writeback.list_tasks` | `pull→gateway`、`sync→sellable` 等 |
| **M8** | `monitor.overview/pull_watermark/audit_backlog/writeback_failures/abnormal_realtime` | 内部使用 |

### 8.2 「只读接口优先」的具体含义

1. **跨模块读数据** → 必须走对方的只读接口（`contract.py` 导出），**禁止**直接 import 对方的内部查询函数
2. **跨模块写数据** → 允许调用对方的公开写接口（同样从 `contract.py` 导出），但：
   - 调用方须在本模块 `contract.md` 的「允许的跨模块调用」段登记
   - 门禁 R2 检查 import 来源；R3 检查表所有权（写操作最终落到 owner 模块的表）
3. **不引入消息队列 / Saga** → 保持关键域强一致，与你的约束一致
4. **预留**：将来若某条边需要异步化，`contract.py` 的接口签名不变，只需在实现内部换成 outbox 事件

| 门禁 | 检查内容 | 工具 | 上线策略 |
|---|---|---|---|
| **依赖方向** | R1 底层不依赖高层；R2 跨模块只走 contract | `tools/check_deps.py` | 先 warn 2 周 → fail |
| **表所有权** | R3 一表一写者 | `tools/check_table_ownership.py` | 先 warn → fail |
| **上下文体积** | R4 单 service ≤ 500 行、单模块 ≤ 12 文件 | `tools/check_context_size.py` | 先 warn → fail |
| **契约一致性** | 代码枚举 ↔ DDL COMMENT ↔ SRS 流转表 | `tools/check_contract_ddl.py` | **直接 fail**（纯机器判定，无误伤空间） |

**例外机制**：确需违规时用 `# arch: allow: <原因> <台账编号>` 注释跳过，并在 `docs/架构-例外台账.md` 登记原因与撤销条件。

## 十一、未来真要拆进程时的路径（现在不做，但边界已预留）

契约定稿后，把任意模块抽成独立服务只需三步：

1. `app/modules/m7_integration/` → 独立仓库/包，`contract.py` 的公开面不变
2. `contract.py` 的实现内部，把进程内调用换成 HTTP/MQ（**调用方零改动**）
3. 数据从「共享库读写」迁移到「独立库 + 只读副本 + 出站事件」

**关键前提**：只有当 (a) 模块契约稳定 ≥ 1 个批次、(b) 该模块有独立的伸缩/发布诉求、(c) 强一致约束允许降级 —— 三者同时成立才动手。
