## 4. 复盘发现的真实缺陷（4 个 · 全部已修）

### 缺陷 1（安全 · 高）同端互踢后旧 access_token 仍然有效

| 项 | 内容 |
|---|---|
| 现象 | 同端二次登录踢掉旧会话后，旧 token 仍能通过 `/auth/me`（200） |
| 根因 | JWT payload 只有 `sub/tid/roles_ver/typ/iat/exp`，**无会话标识**；`validate_access` 只校验「该账号有任一端会话存在」，无法区分是哪个会话 |
| 违反 | SRS-D10.02 FR-05c（同端互踢）+ FR-05b（即时吊销） |
| 修法 | ① `create_access_token` 增加 `sid`（session_id）声明 ② 签发时把 `session_id` 写入 payload ③ `validate_access` 用 Redis `mget` 取该账号全部会话值，校验 token 的 `sid` 是否仍在其中 |
| 影响面 | 同秒签发的两个 token 完全相同 → 被踢会话 2 小时内仍可操作 |
| 验证 | `test_same_device_login_kicks_previous` / `test_logout_deletes_redis_session` 守住 |

### 缺陷 2（资损 · 高）金额勾稽容差边界因浮点误差误判拒单

| 项 | 内容 |
|---|---|
| 现象 | 大额单（35,195.30 元）被**硬失败拒单**，订单进不了缓冲池 |
| 根因 | `check_amount_consistency` 用 `abs(sum_paid - expect) > 0.01`；而 `33435.54 - 33435.53 = 0.010000000002037268 > 0.01` → 「恰好差 1 分」被判超差 |
| 同类问题 | `allocate()` 里 `abs(p_sum - platform_subsidy) <= TOLERANCE` 同样误判 → 行级分摊被错误回退比例分摊 |
| 违反 | SRS-D03.01 FR-06a 金额恒等式（容差 0.01 的本意是「允许差 1 分」） |
| 修法 | 新增 `_diff_cents(a,b)`：把金额差换算成**「分」的整数**再比较（`abs(round(a*100) - round(b*100))`）；两处比较全部改用整数分 |
| 附带修复 | 第 95 行「行优惠不超过行原价」原本是**单边比较**，误改成双边会触发缩放导致行实付归零 —— 已还原为单边并用整数分比较 |
| 验证 | 场景矩阵 `big_amount` 场景；`test_outbound_cmd_status_closed_when_fulfilled` 等回归 |

### 缺陷 3（安全 · 高）认证链路时间基准不统一 → 锁定账户可能被误放行

| 项 | 内容 |
|---|---|
| 现象 | CI 库上「锁定中的账户」登录返回 **200**（应为 423 ACCOUNT_LOCKED） |
| 根因 | `lock_until` / `expire_time` 是 MySQL `DATETIME`（**无时区**），而应用用 `datetime.now()`（本地 +08:00）比较；当 DB 容器时区（UTC）与应用时区不同，写入的锁定期被判定为「已过期」→ **自动解锁放行** |
| 风险 | 生产部署若 DB 与应用主机时区不同，**连败锁定形同虚设** |
| 修法 | `auth.py` 新增 `_utcnow()`（UTC naive），认证链路 4 处时间基准全部统一为 UTC → 与 DB 服务器时区无关 |
| 验证 | `test_locked_account_rejected_with_code` / `test_lock_expires_auto_unlock` |

### 缺陷 4（数据一致性 · 中）模拟器行级优惠分摊有舍入残差

| 项 | 内容 |
|---|---|
| 现象 | 大额单场景下 `Σ行级平台承担 = 1759.76 ≠ 头级 1759.77` |
| 根因 | 模拟器逐行 `round(platform_bear * line/total, 2)`，残差未归位 |
| 影响 | 平台报文金额不自洽 → OMS 侧金额勾稽拒单（真实平台必然满足该恒等式） |
| 修法 | 模拟器把残差补到**金额最大的行**，保证 `Σ行 == 头` |

### 缺陷 5（测试可靠性 · 中）E2E 脚本清理不完整 → 污染开发库并**绕过其他测试的校验**

| 项 | 内容 |
|---|---|
| 现象 | `test_master` 的 4 条用例突然全红，但单跑也红；根因是库里残留了 W6 E2E 自造的 `W6E2ENODE_BR`（owner_co, parent_id=0） |
| 传导链 | `test_master` 取「第一条 parent_id=0 的根节点」→ 取到残留的 **owner_co** 而非 group → `CHILD_MATRIX["owner_co"]` 允许挂 shop → **层级矩阵校验被绕过**（应 422 实得 200） |
| 根因 | W6/W7 E2E 只在**运行开头**清理自造数据，最后一次运行的残留永久留在库里 |
| 修法 | ① 三个 E2E 脚本（fulfill / wms_channel / writeback）**结束时也清理**（自造数据统一用独立前缀 `DLVE2E%` / `W7WB%`，不与演示数据 `DLVW7DEMO%` 冲突）② `test_master` 改为按 `node_type == "group"` 精确定位根节点，不取「第一条」③ 清理语句按 **FK 顺序**（先子表后父表；`gw_api_fail` → `gw_writeback_task`） |
| 附带发现 | 复盘初版「表使用率」工具误报 322 张零引用，实为检测缺陷（只搜表名字符串未搜 ORM 类名）→ 已改为按 ORM 元数据反查：**62 张已建模表 100% 有代码使用** |

### 4.1 另修复的 3 个测试/脚本级问题（非产品缺陷）

| # | 问题 | 修法 |
|---|---|---|
| 5 | 场景矩阵在 CI 里排在履约 E2E **之前**，其 cleanup 删掉了履约 E2E 的前置数据 → 履约 E2E 42/43 | CI 顺序调整：场景矩阵移到履约 E2E **之后**（Job 7b） |
| 6 | W7 通道 E2E 的 SC-03 用 `bm_id + 1` 造第二行 → CI 空库无该物料 → **指令组装整单失败**（lines=[]），两条断言静默不跑 | E2E 现场自造第二物料；且不能用同一物料（行匹配按 bm_id 会永远命中首行） |
| 7 | `ord_receiver` 列名误用 `receiver_district`/`receiver_address`/`buyer_message`（真实列名是 `district`/`address_enc`，留言在 `ord_order.buyer_memo`） | 逐列核对真实 DDL 后修正 |

> **第 6 项特别说明**：断言「静默不跑」比「断言失败」更危险 —— 门禁显示 21/21 通过，实际少了 2 项覆盖。已通过「双库断言数 diff」机制发现（开发库 23 / CI 库 21）。**后续每轮复演应对比断言条数，不只看通过/失败。**
