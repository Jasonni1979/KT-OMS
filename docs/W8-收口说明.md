## 三、本轮修掉的 6 个真实缺陷

| # | 缺陷 | 级别 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | **审单链路在生产上完全不可用** | 严重 | `register_audit_chain/register_audit_plugins` 只有 2 个 seed/E2E 脚本手动调用 → API 服务里审单一跑就 `KeyError: 链未注册`。**没被发现的原因：audit_e2e 自己注册了链，把问题盖住了** | `audit_engine` 模块导入期幂等注册 |
| 2 | **可空列让审单直接 500** | 严重 | `ord_order_item.weight` 是可空列，`load_context` 里 `float(it.weight)` 遇 NULL 抛 TypeError | 新增 `_num()` 兜底 |
| 3 | **`GOODS_UNBOUND` 无产出路径** | 中 | 类型与原因码字典都配了，但插件链里没有插件产出该码 → 未绑定商品永远不落异常单 | 新增 `GoodsMatchPlugin`（CHECK 段，判定 `bm_id=0`） |
| 4 | **订单列表接口 500** | 严重 | `OrderOut.buyer_nick/warehouse_memo/buyer_memo` 声明非空 str，DDL 里是可空列 | 改为可选 |
| 5 | **订单详情接口 500** | 严重 | `OrderItemOut.platform_oid/bm_name/bom_version` 同样问题 | 改为可选 |
| 6 | **条码列表接口 500** | 严重 | `BarcodeOut.material_bn/material_name` 在 `inv_barcode` 表里**根本不存在这两列** | 改为可选 |

### 一个结构性教训

> **pydantic schema 声明必填 ≠ DDL 列 NOT NULL。**
> 两者不一致时，接口在**真实数据**上会 500，而单测往往造不出 NULL 数据 → 测不出来。

对策已落地：`backend/tests/test_schema_null_safety.py` —— 用**真实库数据**遍历所有
响应型 schema 做 `model_validate`，任何「声明必填但 DDL 可空」的字段直接失败。
守门测试上线当场又抓到第 6 个缺陷（`BarcodeOut`）。

## 四、关键设计取舍

### 4.1 不重复造轮子
- 换仓直接复用 D03.06 已有的 `DispatchService.dispatch(exclude_branches=...)`
  （它本来就标注了「FR-04b-1 换仓重试」）+ `PlanExecutor.execute`
- 可用量用 `StockLedgerService.get_balance`（与审单 `stock_check` 同源的 D04.02 唯一公式）
- 分派规则复用 D03.03 的 `ord_dispatch_rule` 表（不另建表），只扩展维度；
  条件求值语义与 `DispatchService._conditions_hit` **完全一致**
- 叫回复用 W7 的 `OutboundCommandService.recall`
- 发号器复用 `OrderBnGenerator`（Redis → DB 号段 → UUID 三级降级）

### 4.2 扩展位不伪造数据
| 能力 | 状态 | 返回 |
|---|---|---|
| 借调建议（D04.05 额度服务） | W8 不做 | `borrow_stock: {enabled: false, reason: "..."}` |
| 转售后（D05 售后服务） | W9 | `enabled: false` + 原因，**不落任何 `aft_refund` 记录** |
| 平台退款 | W9 | `enabled: false` + 原因 |
| OA 推送（强制放行） | W8-3 起 | 落库留痕 + `oa_push: "pending"` 待办标记 |

测试**专门断言了这些扩展位不产生假单据**。

### 4.3 DDL 是权威
本轮又一次印证：异常类型的 `action_set`、原因码映射、异常类型清单，全部以 DDL
预置为准，而不是 SRS 文本。E2E 里「越权动作被拒」是**正确行为**（FR-02d 的落地证据）。
