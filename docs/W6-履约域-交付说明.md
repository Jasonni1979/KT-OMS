## 2. 关键机制（对商派的实质改造）

### 2.1 分仓：决策与执行分离（FR-05a）
商派选仓结果就地写内存订单组与发货单、无决策留痕。本实现输出**不可变 plan**：
- `ord_dispatch_plan` 按 `round_no` 追加，生效 plan = 最新未 superseded 的一份；
- plan 只表达「行→仓→分配量」，**不做任何库存承诺**——真正承诺在 D04.03 预占；
- 消费方：审单引擎 / 拆单策略 / 预占 / 发货单溯源。

### 2.2 分仓：三元满足度 + 行级货主硬约束（FR-03a / FR-01c）
```
满足率(W) = Σ min(available(W, sku, 行货主), need(i)) / Σ need(i)
```
- available 走 `StockLedgerService.available_of`（D04.02 全局唯一公式，禁止另算）；
- **单一归属仓只发自己货主的货**（行级硬约束，手工改仓也不可绕过）；
- 一次批量预取（Redis MGET + DB 批量兜底），**DB/Redis 交互次数与仓数、SKU 数无关**（FR-03e）。

### 2.3 分仓：DOM 埋点（FR-08a，V1.2 友商对标新增）
每次分仓决策写 `ord_routing_decision_log`：候选仓集合 / 各仓特征（可用量·满足率·来源·优先级）/ 命中规则 / 最终选仓 / 耗时 / 成本对比（拆单 vs 等货 vs 调拨，FR-08b）。
这是 Gartner DOM「多目标优化寻源」的数据地基——无埋点则未来无法训练/评估算法。

### 2.4 拆单：策略是纯函数（FR-01a）
```
allocate(input: SplitInput) -> SplitResult   # 无落库/不改单/不查库/无随机
```
- 商派 `splitOrder` **就地修改内存订单组**，失败现场脏（逆向文档 02 §11.5 教训）；
- 本实现策略只算不落库，引擎统一编排落库（FR-03c 单事务，失败整体回滚）；
- 库存视图由引擎**一次批量预取**注入 context，策略内零查库（FR-02c）。

### 2.5 拆单：守恒校验显式化（§5.4）
```
∀ 行 i:  Σ(组内分配量) == 未拆余量(nums - split_num)  且  每条 > 0
```
- 覆盖两类商派未防的 bug：**丢行**（资损）与**重复分配**（超发）；
- 违反 → `CONSERVATION_VIOLATION`，整体失败不落库 + 最高级告警。

### 2.6 拆单：按货主拆是凯淳特色（FR-05，SRS-00 契约）
- 商派无货主模型；本实现按明细行货主分组，每组发货单携带唯一 `owner_id`；
- **D08 分账依据**：买断货主发货单 → 自营收入 + 存货成本结转；代销货主发货单 → 服务费/佣金口径；
- 跨货主订单 + 规则链无 owner 策略 → **引擎层拒绝执行**（`CONFIG_INVALID`），防混货主发货单落库。

### 2.7 发货单：表驱动状态机（§5.1 权威流转表）
```
draft → pushed → processing → outbound → shipped → finished
分支：push_failed / recalling → recalled / rejected / cancelled / partial_outbound
```
- 状态变更**唯一入口** `transit()`：表驱动校验 → 行级锁 → 落库 + `delivery_log` 同事务；
- **非法跳态拒绝并告警**（草稿直接确认 / 出库后取消）；
- 四指令：推送 / 叫回 / 恢复 / 确认——指令与状态分离，中间态保证分布式动作期间可观测可对账。

### 2.8 发货单：出库回传七步编排（§5.3）
```
① 行匹配（回传明细↔发货单行↔订单行 detail 溯源）
② 逐行 settle（预占转扣减，freeze-N & store-N 原子）
③ 差异处理（少发释放 / 多发直扣 + 差异登记）
④ 包裹/称重/运单落库
⑤ 状态流转（partial_outbound / outbound）
⑥ 发货确认（齐套自动）
⑦ 发布事件
```
- 幂等键 = `delivery_id + batch_no`，重复回传忽略；
- settle 失败**不阻塞**状态落库 → 补偿队列 + 每日对账兜底。

## 3. W6 实现的 3 个拆单策略

计划「拆单 3 策略」按 SRS 依据定为：

| split_type | 名称 | 依据 | 级联兼容清单 |
|---|---|---|---|
| `owner` | 按货主拆 | FR-05 凯淳货权分离核心（SC-01） | branch / weight / volume / goods_type |
| `branch` | 按仓库拆 | SC-02（消费 D03.06 分仓 plan） | owner / weight / volume |
| `stock_depth` | 按库存深度拆 | SC-08 部分拆分与续拆、SC-09 失败兜底 | branch / owner |

**注册表架构支持后续零引擎改动新增策略**（FR-01b / AC-14）：实现 `allocate` + `validateConfig` + `getSpecial` + `describe` 四接口后注册即可，规则保存期自动获得 schema 校验与级联兼容校验。

| # | 问题 | 根因 | 修复 |

| 1 | **DDL 列名偏差第四次同款坑** | `ord_dispatch_plan` 无 `update_time`/`version`/`is_deleted`；`ord_delivery_package` 无 `is_deleted`；`ord_delivery_diff` 无 `version`；`ord_order_item`/`ord_order` 多处缺列 | **新增 `tools/check_model_ddl.py`**——逐表逐列比对 ORM 声明与 information_schema，不一致即退出码 1，已接入 CI 复演。62 张表全部一致 |
| 2 | **货主仓属过滤语义做反** | 实现成「仓须服务全部行货主」→ 全候选被过滤光 | 改为行级约束：行只能落到服务其货主的仓（SC-04「各行独立分仓」）；仓作为整单候选 = 至少服务某一行货主 |
| 3 | `org_node_relation` 查询带 `is_deleted` | 该表**无** `is_deleted` 列 → SQL 报错 | 去掉该条件 |
| 4 | `inv_material` 自造数据列名错 | 真实列是 `is_ctrl_store`（非 `is_ctrl`）、`status` 是 tinyint（非 varchar）、无 `unit_cost` | 按真实 DDL 改写 INSERT |
| 5 | `org_owner` 自造数据缺 `org_node_id` | 该列 NOT NULL（货主必须挂组织树） | E2E 脚本先建 `org_node` 再建 owner |
| 6 | CI 空库跑不了跨货主场景 | 空库只有 1 个货主有库存 | E2E 脚本**自造**第二货主 + 独立仓 + 库存（含物料/组织节点补齐） |
| 7 | MySQL REPEATABLE READ 下 ORM 看不到其他连接刚提交的数据 | 造单用独立连接（`engine.begin()`），当前 session 快照是旧的 | 造单后 `await s.commit()` 刷新快照 |
| 8 | `create_from_plan` 的 `branch_id` 为 0 | owner 单策略的组 attrs 不带 branch_id | 组无 branch_id 时按组内行从分仓 plan 兜底取仓 |
| 9 | `split_num` 双重累加 | `createFromPlan`（D03.07 FR-03a）已回写进度，测试又调 `write_progress` | 明确职责：D03.07 负责进度回写（同事务）；`SplitService.write_progress` 仅用于无发货单产出的场景 |

**规律沉淀**：**每新域必须逐表 desc 核对 DDL，不能照抄其他域的基类**——本轮已把它固化成自动化门禁（`check_model_ddl.py`），下次不再靠人肉核对。
