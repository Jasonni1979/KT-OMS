## 二、发现的问题与修复

### 问题 1（严重）覆盖统计工具的模块映射表陈旧 → 覆盖率是**假数字**

| 项 | 内容 |
|---|---|
| 现象 | 覆盖报告显示 **D02.01 = 4%、D10.02 = 18%**，而实际这两个模块各有 16 / 24 条用例 |
| 根因 | `tools/review_coverage.py` 的 `PREFIX_TO_SRS` 映射表未登记 W8 新增的前缀（GW/ACC/SHOP/ABN/ABNACT/ABNAPI/STOCKOUT/MODIFY/AFT/SCHEMA）→ 这些模块的用例**完全不参与统计**（既不贡献显式覆盖也不贡献模块级触达） |
| 修法 | ① 补齐 11 个前缀映射 ② 加**自检函数** `check_prefix_coverage()`：比对 `test_case_map.MODULES` 与映射表，缺一个就报错 |
| 修正后 | 覆盖率 **92% → 98%**；D02.01 **4% → 100%**；D10.02 **18% → 48%** |
| 剩余 48% | **真实缺口** —— D10.02 未覆盖的 17 条是「外部租户门户 + 企微扫码 + 短信验证码登录 + SSO/OIDC」，不在当前 MVP 范围（当前是内部租户 + 账密登录） |

> **教训**：新增测试模块时，必须同步更新覆盖工具的前缀映射，否则统计数字会**静默失真**且没人察觉（92% 看起来很正常）。

### 问题 2（严重）`audit_e2e` 一直是坏的，且**不在 CI 门禁里**

| 项 | 内容 |
|---|---|
| 现象 | 单独跑 `audit_e2e` → **3/5 失败**，但 CI 门禁全绿（因为它没进门禁） |
| 失败 1 | 插件数断言硬编码 `len(plugins) == 9` → 我加 `goods_match` 后变 11 → 断言失效 |
| 失败 2 | 断言「一定有 plan」→ 但插件链 HOLD（如 `NO_BRANCH` 无候选仓）时**本就不产出 plan**（决策=manual 转人工） |
| 修法 | ① 改为断言**核心插件齐备**（不硬编码数量）② plan 断言**分情况**：有 plan → 断言 plan_id；无 plan → 必须是 manual/pool 决策且已落结构化原因 |
| 加固 | **纳入 CI 门禁**（Job 6c，断言数下限 5） |

### 问题 3（严重）`ord_risk_list` 名单有效期判定读**过期 ORM 快照**

| 项 | 内容 |
|---|---|
| 现象 | 已过期的名单（`effective_end` 在过去）**仍然命中** → 黑名单/灰名单判定失效 |
| 根因 | `match_list` 在 **Python 侧**对 ORM 对象判断有效期，而同一会话里 `UPDATE` 过但未 `refresh` 的对象**读到旧值** |
| 修法 | 有效期过滤**下推到 SQL**（`or_(effective_start IS NULL, effective_start <= now)` 等） |

### 问题 4（中）测试用 `DB NOW()` 改时间 → **永远不过期**

| 项 | 内容 |
|---|---|
| 现象 | 名单生效期测试失败：明明把 `effective_end` 改到过去，仍判未过期 |
| 根因 | DB 的 `NOW()` 是**本地时区（+08:00）**，应用比较用 `utcnow()`（**UTC**）→ 改出来的时间在应用侧看是「未来」 |
| 修法 | 测试统一用**应用同基准**（UTC）改时间 |
| 关联 | 这是复盘已记录的「DATETIME 无时区」老坑的**第三次复发**（前两次：认证链路、库存锁） |

### 问题 5（中）`SessionFactory()` 不自动提交 → 跨会话读不到刚写的数据

| 项 | 内容 |
|---|---|
| 现象 | 跨域 E2E 里造的异常单，下一段用另一个 session 查 → `异常单不存在` |
| 根因 | `async with SessionFactory() as s:` **不自动 commit**（只有 `session_scope()` 才提交） |
| 修法 | 显式 `await s.commit()`，并在代码注释里写明这个坑 |

## 八、第三轮检查：真实数据一致性体检（新增常驻门禁）

前两轮都是**静态**检查（类型/覆盖率/方法触及）。静态检查看不出**跨域引用悬空**
—— 故第三轮用**真实库数据**做一致性体检。

### 新增 backend/app/scripts/data_consistency_check.py（12 项体检 + 修复模式）

| 体检项 | 检查什么 |
|---|---|
| 缺货明细 → 异常单 | 引用不能悬空 |
| 缺货明细 → 应急批次 | batch_id 引用 |
| 异常单 → 类型字典 | 类型不能悬空 |
| 异常单 → 订单 | 引用不能悬空 |
| 异常单已解决 → 审单原因 | 标记不能泄漏（应已清零） |
| 异常单未闭环 → 审单原因 | 原因不能丢失（应有 open） |
| 订单行 → 基础物料 | 引用不能悬空 |
| 发货单 → 订单 | 引用不能悬空 |
| 退款单已退款 → 订单 pay_status | 联动不能漏 |
| 售后单在途 → 订单「售后中」标记 | 标记不能漏 |
| 售后申请行 → 申请单 | 引用不能悬空 |
| 退款单 → 售后申请单 | 引用不能悬空 |

### 体检发现的 2 个真实数据不一致

| # | 不一致 | 条数 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | **孤儿缺货明细**（异常单已删、明细残留） | 17 | 测试清理函数只删异常单、**漏删子表明细**；且清理顺序应「先子表后父表」 | ① 修 2 个测试文件的清理（补删子表 + 顺序修正）② 体检脚本加 `--fix` 模式自动清孤儿 |
| 2 | **悬空异常单**（订单已删、异常单残留） | 8 | 同上（演示/测试数据清理不彻底） | 同上（`--fix` 自动清） |

### 顺带修掉体检脚本自身的一个坑
修复 SQL 最初写成 `DELETE s FROM tbl s WHERE ...`（**多表删除语法要求默认库**）
→ 在 `docker exec` 里报 `No database selected` 且**错误被静默吞掉**（修复报 0 条）。
改为「单表 DELETE + IN 子查询」后正常。

### 纳入 CI 门禁
`Job 3c/4: 跨域数据一致性体检` → CI 复演 **34/34 全绿**。
体检支持 `KTOMS_MYSQL_CONTAINER` 环境变量（CI 复演库 / 本地开发库）。

## 九、本次检查沉淀的检查规范（写进项目记忆）

1. **新增测试模块必须同步更新 `tools/review_coverage.py` 的 `PREFIX_TO_SRS`**，
   否则覆盖率统计**静默失真**（本次 92% → 实际 98%，D02.01 4% → 实际 100%）。
   自检函数已内置：`check_prefix_coverage()`。
2. **E2E 脚本不能游离在 CI 门禁之外** —— `audit_e2e` 坏了很久没人发现，
   因为没人跑它。本次全部 8 个 E2E 套件都在门禁里，且都带**断言数下限**。
3. **断言不要依赖"环境恰好有数据"** —— `audit_e2e` 取"库里任意订单"，
   遇到无仓库绑定的订单就必然失败。断言必须**分情况**（有 plan / 无 plan）。
4. **不要硬编码集合大小** —— 插件数 `== 9` 在加一个插件后就失效。改为断言
   **核心成员齐备**。
5. **ORM 对象可能是过期快照** —— 同会话内 UPDATE 后未 refresh 的对象读到旧值。
   涉及数据新鲜度的过滤**下推到 SQL**。
6. **跨会话写数据后必须显式 commit** —— `SessionFactory()` 不自动提交。
7. **改时间必须用应用同基准（UTC）** —— DB `NOW()` 是本地时区，与应用的
   `utcnow()` 不同基准，改出来的时间在应用侧看是「未来」。
8. **测试/演示数据的清理必须「先子表后父表」** —— 否则子表残留成孤儿记录
   （第三轮实测 17 条孤儿缺货明细）。且清理函数要覆盖**所有**自造数据的子表。
9. **静态检查看不出引用悬空** —— 必须有「真实数据一致性体检」门禁
   （`app.scripts.data_consistency_check`，已入 CI）。
