### 顶层目录结构

```
OMS-main/
├── app/            # 58 个业务模块（核心）
│   └── <module>/
│       ├── app.xml        # 模块元信息（名称/描述/版本/依赖）
│       ├── desktop.xml    # 后台菜单与权限挂载点
│       ├── controller/    # 控制器（admin/ 后台 + api/ 接口）
│       ├── model/         # 业务模型（核心业务逻辑所在）
│       ├── dbschema/      # 数据表定义（一表一文件，PHP 数组 DSL）
│       ├── dbevent/       # 数据库事件钩子（表写入后触发）
│       ├── dbprocedure/   # 存储过程
│       ├── task.php       # 定时任务定义
│       ├── services.xml   # 服务注册（跨模块调用接口）
│       ├── lib/           # 模块内部类库
│       ├── lua/           # Lua 规则脚本（ome 自动规则）
│       ├── view/          # 模板
│       └── initial/       # 初始化数据 SQL
├── config/         # 部署配置（deploy.xml、mapper.php）
├── data/           # 运行时数据（导入导出临时目录）
├── docker/         # Docker 部署
├── public/ assets/ # 静态资源
├── tests/          # phpunit 测试
└── tools/          # 辅助工具
```

### 框架关键机制（重写时的架构启示）

1. **dbschema DSL**：表结构以 PHP 数组声明，同时承载 UI 元数据（label/width/in_list/filtertype）——即"模型驱动界面"，列表页、筛选器由 schema 自动生成。**这是它开发效率高的核心，重写时值得借鉴思想（元数据驱动 CRUD），但不必绑定 PHP。**
2. **services.xml 服务注册**：模块间通过服务名解耦调用，而非直接 include。
3. **dbevent 数据库事件**：表写入后触发钩子（如订单状态变更联动库存），事件驱动解耦。
4. **Swoole 秒级队列 + taskmgr**：异步任务（平台拉单、库存同步、推仓）全部队列化。
5. **Lua 规则引擎**（ome/lua，11 个脚本）：订单自动审核/分配规则可热更新。

## 3. 代码量分布的解读（给重写的启示）

1. **erpapi（1,411 文件）是最大的模块但不是核心**——它是各平台 API 的适配层堆叠（淘宝 TOP、京东 JOS、拼多多、抖音等的签名/请求/报文转换）。重写时这层的价值是**报文与平台规则参考**，架构上应该做成适配器插件化，而非像商派一样堆成一个巨型模块。
2. **ome（1,127 文件、196 张表）是真正的心脏**——订单、会员、商品、库存、发货、支付全在里面，属于"大内核"设计。重写时应按 DDD 拆分为订单中心、商品中心、库存中心、售后中心等独立域。
3. **711 张表偏多**，其中 archive 模块 36 张是主表镜像（归档方案）、console 55 张是运维面板。真正的核心业务表约 500-600 张，重写时通过合理的域拆分与字段精简，预计可压缩 30-50%。
4. **行业特化模块可裁剪**：goldentra（黄金）、tgkpi（拣货绩效）、pos、wap 等按凯淳业务取舍。
5. **对凯淳代运营场景高价值模块**：organization（多品牌组织隔离）、dealer（经销）、purchase、inventorydepth（库存深度）、tgstockcost（成本核算）、finance + logisticsaccounts（结算对账）、omeauto（自动规则引擎）、taoguan*/erpapi（平台对接）。
