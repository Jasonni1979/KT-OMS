商派 ONEX OMS 逆向工程总览报告
从 113 万行开源代码到自研重写的完整知识地图

对 ShopeX/OMS（商派 ONEX OMS，Apache-2.0，main @ 2026-10-21）全量源码做静态逆向： 58 个业务模块、711 张数据表、四大业务域流程逐一还原，产出 6 份工程文档（约 43 万字节 Markdown，29 张 Mermaid 图）。 本报告为总览与决策摘要，明细见 商派OMS逆向文档/ 目录。

协议：Apache-2.0 · 可闭源商用 代码基线：v8.3.0 后 main 分支 逆向时间：2026-10-23 方法：静态分析 · 未动态运行

1核心结论

结论 1：商派 OMS 的业务模型完整度足以作为自研重写的「需求底稿」，逆向路线成立

订单（三套状态机 + 规则引擎审单 + 16 种拆单策略）、库存（三层主体 + Redis/Lua 预占 + 出入库流水）、采购经销（38 表全链路 + 供应商台账）、财务（AR/核销/账期/运费对账/发票）、平台对接（77 个平台通道目录 + 五层 API 框架）——电商代运营 + 经销双场景所需的业务模型全部在源码中有可验证的成熟实现。重写时不需要从零发明业务规则。

结论 2：值得整体借鉴的是 7 个「机制级」设计，而非代码本身

① schema DSL 元数据驱动 CRUD；② 审单插件链 + 位标记；③ 合单指纹预计算 + 缓冲时间窗；④ 拆单策略注册表；⑤ 预占走独立流水表 + Redis Lua 原子操作（不落库存主字段）；⑥ api_log/api_fail 双表 + 错误码分级重试；⑦ 售后「申请单/执行单/退款单」三段式。这 7 个机制是商派 20 年电商 ERP 沉淀的精华，全部可以在新技术栈上重新实现。

结论 3：商派架构有 4 个明确缺陷，自研时必须规避

① ome 大内核（196 表 1127 文件混装订单/商品/会员/库存/售后）→ 应按域拆分；② erpapi 巨型适配层且强依赖商派矩阵中心（SaaS 网关）→ 平台对接必须自建 gateway；③ 每平台一张售后镜像表（15 张 return_product_*）→ 应改 JSON 扩展列；④ 财务单据不带货主维度 → 多品牌代运营场景必须补上（这是原系统最大业务缺口）。

合规声明

ShopeX/OMS 为 Apache-2.0 协议：阅读源码、产出内部分析文档、借鉴业务模型、乃至复用代码后闭源商用均被允许（需保留版权声明与 NOTICE）。本逆向文档集只提取业务模型与流程逻辑，重写阶段不复制代码，无传染风险。工作底稿（schema.json / 提取脚本）保存在 _research/，全程可复现。

4四大业务域流程速览

4.1 订单全生命周期（文档 02）

平台拉单/导入→ 缓冲池聚组→ 审单规则引擎（23插件位）→ 拆单（16策略）→ 合单（指纹分组）→ 配货分仓→ 生成发货单/推仓→ 发货回传→ 完成/归档
  • 三套状态并行：process_status（确认/拆分）× pay_status（9 值）× ship_status（5 值）+ 总状态 status + 一批布尔辅助位（pause/abnormal/is_fail/is_not_combine/archive）。
  • 审核即履约路由：自动审单一次性完成选仓+拆单+选物流+合单+生成发货单；通过即推仓，不通过按位标记写入原因并分派人工审核组。
  • 拆单不产生新订单：拆分结果是「一单多发货单」，orders.splited_num + order_items.split_num 记录进度。
  • 合单指纹预计算：拉单时算好 combine_hash，「付款后等 N 分钟」缓冲窗换合单率——低成本高收益，值得照搬。
  • 复审快照机制：客服改单前快照+冻结库存+对比回滚，是处理改单风险的成熟方案。

4.2 库存与仓储（文档 03）

销售物料 SKU→ BOM 拆解 → 基础物料 BM→ 按仓拆分 → branch_product（仓×SKU 记账行）→ iostock 出入库流水→ 成本核算/库存深度回写
  • 三层库存主体：销售物料（可组合装）→ 基础物料（最小管理单元）→ 仓库×物料（记账行：实际 store / 冻结 store_freeze / 在途 arrive_store / 成本 unit_cost）。
  • 预占不落主字段：订单占用走独立预占流水表 + Redis Lua 原子操作，这是商派高并发的关键设计，重写必抄。
  • 五口径库存：实际/可用/锁定/在途/次品，退货按良/不良质检分别入正品/次品库存。
  • 成本核算：tgstockcost 移动加权平均，出入库流水驱动。

4.3 采购经销与财务（文档 04）

采购申请→ 采购单（5状态分离）→ 到货入库（在途-）→ 对账单（期初/增加/已付/期末）→ 付款核销
  • 现购按单挂账、赊购按入库挂账：符合财务实务（票到付款 vs 货到挂账），抽象为「应付单生成策略」。
  • dealer 授权模型：BU→贸易公司→经销商→店铺四级组织 + 产品线授权到店（SKU 级、带时间窗、自发/代发切换），高度契合多品牌代运营；但缺账期/信用额度，需自建。
  • 转单按货权主体分组拆单：货权分离的关键机制，必须保留。
  • 财务四件套：AR/Bill/核销/账期 +「客户实付 vs 平台承担」双口径金额，核销分正常/差异/强制三档。
  • 运费对账：预估/实际双账单按物流单号匹配，记账→审核→关账批次流程。

4.4 平台对接与售后（文档 05）

平台消息 TMC/定时增量/单拉补偿→ erpapi 五层框架→ 水位+幂等键落单→ 发货回传（事件驱动）→ api_fail 分级重试
  • 拉单三保险：平台消息推送 + 定时增量（水位 last_download_time）+ 单拉补偿；幂等键 is_repeat 防重。
  • ⚠ 矩阵中心依赖：商派所有平台 API 经其 SaaS 矩阵中心代理——自研必须替换为自建 gateway（session 托管、限流、平台 SDK 池），这是重写工作量最大的一块。
  • 售后三段式：统一申请单（return_product）+ 仓内执行单（reship）+ 退款单（refund_apply→refunds）；申请归申请、作业归作业、钱归钱。换货 = 退货链路 + 0 元新订单复用正向履约。
  • 平台镜像表模式：15 张 return_product_*（每平台一张）吸收报文差异——重写改 JSON 扩展列。
